# Digital Design, HDLs and FPGAs

Research notes, 2026-09-01. Part 0 of the track builds a CPU from NAND gates upward in a
teaching HDL and then abandons it — the machine exists, it runs, and it is made of nothing.
This is the unit where that design becomes real silicon behaviour: the same adder, the same
register file, the same fetch–decode–execute loop, but now in a language a synthesiser
accepts, verified against a golden model, mapped onto lookup tables, closed against a
timing constraint, and — at the far end — plausibly taped out. It is the one place in the
course where the word "hardware" in the title is literally true.

**Everything in §0 was executed, not recalled.** Commands, outputs and exact warning
strings are reproduced verbatim. Everything else is cited; claims I could not verify are
flagged explicitly in §8.

## 0. TOOLING AVAILABILITY — the finding that shapes every exercise

The brief asked specifically whether Compiler Explorer supports any HDL, and whether
Verilator's C++ output could be compiled there as a checking mechanism. Answers below, all
tested against the live API on 2026-09-01.

### 0.1 Compiler Explorer has no HDL frontend. None.

`GET https://godbolt.org/api/languages` returns **97 languages**. Filtering the full JSON
for `verilog|vhdl|circt|hdl|chisel|fpga|yosys|hardware` yields exactly one hit:

```json
{"id": "circt", "name": "CIRCT", "extensions": [".mlir"], "monaco": "mlir"}
```

There is **no Verilog, no SystemVerilog, no VHDL, no Chisel** frontend, and no Verilator,
Yosys or Icarus. The CIRCT entry exposes exactly one compiler:

```
GET /api/compilers/circt  ->  1 result
circtopt-trunk | CIRCT opt (trunk)
```

`circt-opt` takes **MLIR**, not Verilog. `GET /api/libraries/circt` returns `[]`.

**CIRCT does emit Verilog, though.** Verified — this MLIR input:

```mlir
hw.module @alu(in %a: i8, in %b: i8, in %op: i1, out r: i8) {
  %sum = comb.add %a, %b : i8
  %dif = comb.sub %a, %b : i8
  %o = comb.mux %op, %dif, %sum : i8
  hw.output %o : i8
}
```

with `--export-verilog` produced (exit code 0):

```verilog
// Generated by CIRCT d900741
module alu(	// <source>:1:1
  input  [7:0] a,
               b,
  input        op,
  output [7:0] r
);
  assign r = op ? a - b : a + b;
endmodule
```

So Compiler Explorer has a Verilog **backend** but no Verilog **frontend**. A learner
cannot paste Verilog into godbolt.org and get anything at all. Hand-writing `hw`/`comb`/
`seq` dialect MLIR is not a reasonable beginner exercise. **Treat this as a curiosity, not
a teaching tool.**

### 0.2 Verilator is not on Compiler Explorer, and its output will not build there

No Verilator in the compiler list, and no `verilator` entry among the 199 C++ libraries.
Verilator's generated C++ `#include`s `verilated.h` and links `libverilated.a`, neither of
which exists on CE. **Verilator-output-as-checking-mechanism on Compiler Explorer does not
work.** That idea is dead; do not design around it.

### 0.3 But SystemC IS on Compiler Explorer, and it EXECUTES

This is the useful discovery. The C++ library list contains:

```json
{"id": "systemc", "name": "SystemC",
 "description": "System-level modelling and simulation of hardware designs (IEEE 1666)",
 "url": "https://systemc.org/", "versions": [{"version": "3.0.0", ...}, {"version": "3.0.1", ...}]}
```

Versions offered are **3.0.0 (id `300`) and 3.0.1 (id `301`)**. SystemC is IEEE 1666: a C++
library with `sc_module`, `sc_in`/`sc_out`, `sc_signal`, `SC_METHOD`, sensitivity lists, an
event-driven kernel and **real delta cycles**. It is a genuine hardware simulator that
happens to be a C++ library — which is exactly why it slips through a C++-only sandbox.

I compiled and ran a two-stage shift register through the CE execution API. Sweeping
compiler × standard × library version gave this compatibility matrix:

| Compiler | `-std=` | SystemC | Result |
|---|---|---|---|
| `g142` (GCC 14.2) | `c++17` | 300 / 301 | **executes** |
| `clang_trunk` | `c++17` | 300 / 301 | **executes** |
| `gsnapshot` (GCC trunk) | `c++20` | 300 / 301 | **executes** |
| `gsnapshot` | `c++17` | 300 / 301 | link error |
| `g142` | `c++20` | 300 / 301 | link error |

The failures are an ABI-version symbol mismatch, not a code problem:

```
undefined reference to `sc_core::sc_api_version_3_0_1_cxx201703L::sc_api_version_3_0_1_cxx201703L(...)'
```

The prebuilt library encodes the C++ standard it was built with into a symbol name.
**Pin `g142` + `-std=c++17` + library `systemc` version `301`** and it is stable.

The program that ran:

```cpp
#include <systemc.h>
SC_MODULE(dff) {
  sc_in<bool> clk; sc_in<sc_uint<8> > d; sc_out<sc_uint<8> > q;
  void seq() { q.write(d.read()); }
  SC_CTOR(dff) { SC_METHOD(seq); sensitive << clk.pos(); }
};
int sc_main(int, char**) {
  sc_clock clk("clk", 10, SC_NS);
  sc_signal<sc_uint<8> > a, b, c;
  dff u1("u1"); u1.clk(clk); u1.d(a); u1.q(b);
  dff u2("u2"); u2.clk(clk); u2.d(b); u2.q(c);
  a.write(0);    sc_start(5,  SC_NS);
  a.write(0xAB); sc_start(10, SC_NS);
  std::cout << "1 edge: b=" << b.read() << " c=" << c.read() << std::endl;
  sc_start(10, SC_NS);
  std::cout << "2 edges: b=" << b.read() << " c=" << c.read() << std::endl;
  return 0;
}
```

Actual output:

```
1 edge: b=171 c=0
2 edges: b=171 c=171
```

`171 = 0xAB`. The value took **two clock edges** to cross two flops. That is non-blocking
semantics demonstrated by execution, in a browser, with a shareable URL. `sc_signal` writes
become visible only in the next delta cycle — exactly the `<=` rule. **This is a usable
in-browser vehicle for the concurrency and delta-cycle material**, and it is the only one
Compiler Explorer offers.

Its limit: SystemC teaches the *semantics* but is not Verilog and cannot be synthesised. It
cannot carry the latch-inference or synthesis-warning exercises.

### 0.4 Yosys runs with zero install — locally AND in a browser

`pip install yowasp-yosys` (YoWASP ships FOSS FPGA tools as WebAssembly via PyPI and npm).
Installed into a throwaway venv:

```
Yosys 0.68 (git sha1 38e001a6f, Release, Clang 22.1.0)
```

No compiler, no Homebrew, no system packages. This is the single most important tooling
fact in this report, because Yosys is a **synthesiser** — it checks things no simulator
can. Three exercises verified end to end.

**(a) Inferred latch — the warning is exact and greppable.**

```verilog
module ctrl(input wire [1:0] op, input wire a, input wire b, output reg y);
  always @* begin
    case (op)
      2'b00: y = a & b;
      2'b01: y = a | b;
      2'b10: y = a ^ b;
      // 2'b11 missing -> y must hold its value -> latch
    endcase
  end
endmodule
```

`yosys -p "read_verilog latch.v; proc; opt; stat"` printed:

```
2.8. Executing PROC_DLATCH pass (convert process syncs to latches).
Warning: Latch inferred for signal `\ctrl.\y' from process `\ctrl.$proc$latch.v:2$1': $auto$proc_dlatch.cc:547:proc_dlatch$32
...
        1   $dlatch
Warnings: 1 unique messages, 1 total
```

Two independent machine-checkable signals: the string `Latch inferred for signal` in
stderr, and a `$dlatch` cell in the `stat` listing. A grader is a one-line grep.

**(b) Blocking vs non-blocking — provably different hardware.**

Identical modules, one character different:

```verilog
// nb.v                          // bl.v
always @(posedge clk) begin      always @(posedge clk) begin
  q1 <= d;                         q1 = d;
  q2 <= q1;                        q2 = q1;
end                              end
```

`yosys -p "read_verilog X.v; synth -top shifter; stat"`:

| File | cells | detail |
|---|---|---|
| `nb.v` (`<=`) | **2** | `2 $_DFF_P_` |
| `bl.v` (`=`)  | **1** | `1 $_DFF_P_` |

The non-blocking version is a two-stage shift register. The blocking version optimises down
to **a single flip-flop** — `q1 = d` takes effect immediately, so `q2 = q1` reads the new
`d`, both flops hold the same value every cycle, and the synthesiser deletes one. The whole
lesson, reduced to an integer a script can assert on. **This is the best exercise in this
report.**

**(c) Formal equivalence checking, with no external SMT solver.**

Yosys' built-in SAT solver proves equivalence directly. Golden model vs. the "XOR the B
input and feed carry-in" subtract trick that Ben Eater's ALU uses:

```verilog
module gold(input [7:0] a, input [7:0] b, input sub, output [7:0] y);
  assign y = sub ? a - b : a + b;
endmodule
module gate(input [7:0] a, input [7:0] b, input sub, output [7:0] y);
  wire [7:0] bx = b ^ {8{sub}};
  assign y = a + bx + sub;
endmodule
```

Built a miter and ran `sat -verify -prove trigger 0`:

```
Solving problem with 529 variables and 1440 clauses..
SAT proof finished - no model found: SUCCESS!
   ...  Q.E.D.
```

Deleting the `+ sub` carry-in (the classic bug) instead produced a **concrete
counterexample**:

```
SAT proof finished - model found: FAIL!
   Proof failed!
  Signal Name             Dec       Hex           Bin
  --------------- ----------- --------- -------------
  \in_a                   214        d6      11010110
  \in_b                   199        c7      11000111
```

Both directions work. A learner can *prove* their Part 0 ALU correct across all 2^17 input
combinations in milliseconds, with one pip install and no solver. Compare nand2tetris'
test-vector scripts, which only sample.

**Browser caveat, measured.** YoWASP publishes `@yowasp/yosys` on npm, loadable from
`https://cdn.jsdelivr.net/npm/@yowasp/yosys/gen/bundle.js` (HTTP 200, 0.5 MB). But the real
payload is `/gen/yosys.core.wasm` at **67.2 MB**, fetched at runtime. Consequences:

- On an ordinary web page or a course-hosted site: **works**. This is how a browser-based
  auto-grader for these exercises would be built.
- Inside a Claude Artifact: **will not work.** Artifact CSP permits `<script>` from jsDelivr
  but blocks a library's own runtime `fetch`, and 67 MB exceeds the 16 MB artifact cap
  regardless. Do not plan artifact-embedded Yosys.

## 1. The mental shift that breaks everyone

This is the single biggest conceptual barrier in the topic, and most tutorials fumble it by
opening with syntax. Verilog's syntax is deliberately, misleadingly C-like. That
resemblance is a trap, and the entire first unit should be spent disarming it.

### 1.1 The one-sentence version

> **You are not writing instructions that a machine will execute in order. You are writing
> a description of a structure that exists all at once, forever, and settles.**

Every learner arriving from software carries one assumption so deep they do not know it is
an assumption: that a program is a sequence of steps performed over time by a machine that
reads it. Every line of C, Python, Rust and assembly they have written was a step. The
processor fetched it, did it, moved on. Time was free and implicit; the machine supplied it.

An HDL has no such machine. **There is no processor reading your Verilog. The Verilog *is*
the processor.** Software spends time to save hardware; hardware spends area to save time.
Every confusion below is a corollary of that one inversion.

### 1.2 Assignment is a wire, not an event

```verilog
assign y = a & b;
```

This does not mean "compute `a & b` and store it in `y`." It means **`y` is permanently
connected to the output of an AND gate whose inputs are `a` and `b`.** It is a statement of
fact about the circuit, true at all times, not an action performed at a moment.

Two consequences beginners find shocking:

1. **Order does not matter.** Writing `assign y = a & b;` before or after
   `assign a = c | d;` produces byte-identical hardware. The file is a set of simultaneous
   equations, not a script. Reordering a C program changes it; reordering `assign`
   statements does not.
2. **You cannot assign twice.** `assign y = a; assign y = b;` is not "y ends up as b." It is
   two gate outputs physically wired to the same node — a short circuit. Simulators report
   `x` (contention); synthesisers reject it. In software the last write wins; in hardware
   both drivers fight.

The teaching move: **forbid the word "assign" out loud. Say "connect."** `y` *is* the output
of that gate.

### 1.3 Everything happens concurrently and continuously

A module with ten `assign` statements and three `always` blocks has thirteen things
happening **simultaneously and permanently**. There is no `main`. There is no "currently
executing line." Every gate is always evaluating; when an input changes the output changes
some picoseconds later, and that is all that ever happens.

The mental model is not a CPU stepping through a program. It is **a circuit board where
every component is powered on at once.** Simulation *appears* sequential only because a
simulator is a program pretending to be a circuit (§3.1) — that pretence is an
implementation detail of the tool, not a property of the hardware. The `<=` rule (§2.3)
exists entirely to keep the pretence honest.

### 1.4 A `for` loop unrolls into hardware in space

This is where software intuition fails most violently.

```verilog
integer i;
always @* begin
  parity = 1'b0;
  for (i = 0; i < 8; i = i + 1)
    parity = parity ^ data[i];
end
```

There is **no loop in the resulting hardware.** No counter, no branch, no iteration, and it
does not take 8 clock cycles. The synthesiser fully unrolls this at compile time into **a
chain of 8 XOR gates**, all of which exist physically and evaluate concurrently. The loop
bound must therefore be a compile-time constant — a loop to a runtime variable is not
synthesisable, because you cannot build a variable amount of silicon.

The cost model inverts completely:

| | Software | Hardware |
|---|---|---|
| Loop of N iterations | N × time, 1 × code | 1 × time (one gate-delay chain), **N × area** |
| Doubling N | twice as slow | **twice as big** |
| Unused branch of an `if` | costs nothing at runtime | **the mux and both branches are built and powered** |
| Deeper nesting | more time | longer critical path *and* more area |

That last row matters: in an `always @*` block **both sides of every `if` are physically
constructed.** The `if` becomes a multiplexer selecting between two results that were both
computed. Hardware does not skip work; it computes everything and throws most of it away.
This is why deeply nested conditionals wreck timing (§4.4) — each level adds mux delay to
the critical path.

If a learner wants iteration *in time*, they must build it: a counter, a state machine, and
a datapath the state machine steers. That is not a loop; it is a small CPU. Which is exactly
what Part 0 built — **Part 0's CPU is what "a for loop" costs when you have to build it
yourself.** Make that connection explicit.

### 1.5 The name "variable" is a lie

`reg parity;` does not create a register. `integer i;` does not create a counter. In
`always @*` blocks these are **temporary names for wires** inside a combinational cloud —
scaffolding the synthesiser uses to work out what gates to build, then discards. `i` above
does not exist in the netlist at all; it existed only during elaboration.

A learner who reads `reg` as "storage" will infer latches everywhere and be baffled that
`integer i` did not cost 32 flip-flops. Confront the naming directly (§2.2), early.

### 1.6 The four diagnostic questions

Give the learner these to run on every block they write. They convert the abstract shift
into a checklist:

1. **What gates does this build?** If you cannot sketch it, you are writing software.
2. **How many copies exist?** Every loop iteration, every array element, every `generate`
   instance is real, physical and simultaneous.
3. **Does it hold state between clock edges?** If yes it is flip-flops and needs
   `always_ff`. If no it must be *fully* specified or you get a latch (§2.5).
4. **What is the longest path through it?** That is what sets your clock speed (§4.4).

### 1.7 Where the analogy to Part 0 helps, and where it hurts

nand2tetris' HDL actually gets the mental model **right** — it is purely structural. You
instantiate chips and wire them together. No `always` blocks, no procedural statements, no
assignment-as-event to be confused by. A `.hdl` file is unambiguously a netlist.

So the Part 0 learner arrives with a *correct* intuition and is then handed Verilog, whose
procedural syntax actively invites them to abandon it. **Frame the transition as: "you
already know what hardware is; Verilog is going to try to convince you otherwise, and you
must not let it."** That framing is worth more than any number of gate diagrams.

Four things Part 0 did *not* teach, which land in later sections:

1. **No bus, no tri-state.** Hack multiplexes everywhere. The learner has never met bus
   contention or the `z` value.
2. **No visible time.** The Hack CPU is single-cycle, so "an instruction takes N cycles" was
   never physically observable. Repaired by waveform reading (§3.5) and pipelining (§4.7).
3. **No unknown state.** Part 0 pretended every wire always held a defined 0 or 1. Real
   designs power up unknown; four-valued logic (`0`,`1`,`x`,`z`) exists to model this.
4. **No cost.** In Part 0 a chip was free. Here a design is LUTs, flip-flops, block RAMs,
   DSP slices and routing — a finite budget a report prints out and that you will exceed.

## 2. Verilog and SystemVerilog, properly

### 2.1 Modules and ports

The module is the only unit of hierarchy. A design is a tree of module instances; leaves are
primitives or vendor macros.

```systemverilog
module counter #(parameter int WIDTH = 8) (
  input  logic             clk,
  input  logic             rst_n,
  input  logic             en,
  output logic [WIDTH-1:0] count
);
  always_ff @(posedge clk or negedge rst_n) begin
    if (!rst_n)   count <= '0;
    else if (en)  count <= count + 1'b1;
  end
endmodule
```

Instantiation is structural — this creates a physical copy:

```systemverilog
counter #(.WIDTH(16)) u_ctr (.clk(clk), .rst_n(rst_n), .en(tick), .count(value));
```

**Always use named port connections**, never positional. Positional connection is a silent
miswiring generator, and the failure mode is a design that simulates as nonsense with no
error. Verilog-2001 ANSI port style (above) supersedes the old `module m(a,b); input a;`
form; teach the old form only for reading legacy code.

### 2.2 `wire` vs `reg` vs `logic` — the historical naming disaster

This trips up essentially every beginner, and the reason is historical, not logical.

- **`wire`** is a *net*: it must be continuously driven, by an `assign` or a module output.
  No memory. It can have multiple drivers (resolved, possibly to `x`).
- **`reg`** is a *variable*: it holds the last value procedurally assigned to it, and may
  only be assigned inside `always`/`initial` blocks.

**The trap: `reg` does not mean register.** The name describes a property of the
*simulator's* data model — "this retains its value between assignments" — and says
**nothing** about the hardware. A `reg` assigned in `always @*` synthesises to
**combinational gates, no storage whatsoever**. A `reg` assigned in `always @(posedge clk)`
synthesises to flip-flops. **The distinction lives in the block, not the declaration.**

The bookkeeping Verilog forces on you:

| Assigned by | Must be declared |
|---|---|
| `assign` (continuous) | `wire` |
| inside `always` / `initial` | `reg` |
| module output driven by `assign` | `wire` |
| module output driven in `always` | `reg` |

None of that carries information about the hardware. It is pure bookkeeping about *which
syntax you used*, and it is why beginners write `reg` expecting a flop and get gates.

**SystemVerilog fixes it with `logic`.** `logic` is a 4-state type assignable from either
continuous or procedural context (with the one restriction that it cannot have multiple
drivers — for that you still need `wire`). It removes the bookkeeping entirely.

**Recommendation: teach `logic` for everything from the first line, and explain `wire`/`reg`
purely as legacy you will encounter reading other people's code.** There is no pedagogical
value in making a 2026 learner track a distinction that was a 1984 implementation artefact.
Show the trap so they can read old code, then never use it.

Related: 4-state values are `0`, `1`, `x` (unknown/conflict) and `z` (high impedance — not
driven; this is tri-state, which Part 0's Hack platform never had). `x` in simulation means
"the simulator does not know"; `x` in synthesis means "don't care", and that mismatch is its
own family of bugs.

### 2.3 Blocking (`=`) vs non-blocking (`<=`) — the rule and the reason

**The rule, memorisable, no exceptions worth teaching:**

> **Combinational logic (`always_comb`) uses blocking `=`.**
> **Sequential logic (`always_ff`) uses non-blocking `<=`.**
> **Never mix the two kinds of assignment in one block.**
> **Never assign to the same signal from more than one block.**

Most tutorials stop there. That is a mistake: the rule looks arbitrary until you see the
machine underneath, and a learner who has only memorised it cannot debug the day it bites.

**Why: the stratified event queue.**

The problem the rule solves is genuine. Consider two flip-flops that should form a shift
register:

```verilog
always @(posedge clk)  q1 = d;    // block A
always @(posedge clk)  q2 = q1;   // block B
```

Both blocks wake on the same clock edge. The IEEE 1364/1800 standards deliberately **do not
define which runs first.** If A runs first, `q1` is already `d`, so `q2` gets the *new* value
and you have one flop. If B runs first, `q2` gets the *old* `q1` and you have two. Two
simulators, or one simulator on two days, can legally disagree. This is a **race
condition** — not a simulator bug, but the specification declining to order concurrent
events, because real hardware has no such order either.

Real flip-flops do not have this problem, because a physical flop **samples its input at the
edge and drives its output slightly after** (clock-to-Q delay, §4.4). Old values are read;
new values appear afterwards. Every flop in the design does this at once.

The event queue exists to model exactly that. Within a single simulation time step, events
are sorted into ordered regions. Simplified to what matters:

| Region | Contains |
|---|---|
| **Active** | blocking assignments, `assign` evaluation, `$display` |
| **Inactive** | `#0` delayed events |
| **NBA (Non-Blocking Assign update)** | the *updates* of non-blocking assignments |
| Observed / Reactive | assertions, testbench program blocks |

A non-blocking assignment executes in **two separated steps**:

1. In the **Active** region the right-hand side is **evaluated** and the result stashed. The
   left-hand side is *not yet changed*.
2. In the **NBA** region — after *every* block in the design has finished its Active-region
   work — all stashed values are **written** to their left-hand sides.

So for:

```verilog
always @(posedge clk)  q1 <= d;
always @(posedge clk)  q2 <= q1;
```

Both blocks evaluate their RHS first: A stashes `d`, B stashes **the old `q1`**, because
nothing has been written yet. Then both writes happen. `q2` gets the old `q1`. **Two flops,
deterministically, regardless of which block the simulator visited first.** The race is gone
— not by picking an order, but by making the order irrelevant. That is precisely the
read-then-update behaviour of real silicon, and it is why `<=` is the *non-blocking*
assignment: it does not block the rest of the time step waiting for its own effect.

A blocking `=` evaluates **and writes immediately**, in the Active region, before the next
statement in that block runs. Inside one combinational block that is exactly right, because
you are describing a chain of gates and each temporary should feed the next:

```systemverilog
always_comb begin
  sum = a + b;        // a wire
  y   = sum & mask;   // fed by that wire
end
```

Here `=` is correct and `<=` would be wrong — `<=` would make `y` read the *previous* `sum`,
inserting a phantom cycle of delay that does not exist in the gates.

**Why synthesis agrees.** Synthesisers implement the same semantics structurally:

- `<=` in a clocked block → every left-hand side becomes a **flip-flop**, all sampling
  simultaneously from pre-edge values.
- `=` in a clocked block → the statements are treated as a **sequential dependency chain**
  collapsed into the *same* clock edge, so intermediate values never get storage.

**This is measurable, and I measured it** (§0.4(b)). Same module, one character changed:

| Assignment | Yosys `synth` result |
|---|---|
| `q1 <= d; q2 <= q1;` | **2 cells — `2 $_DFF_P_`** (shift register) |
| `q1 = d; q2 = q1;`   | **1 cell — `1 $_DFF_P_`** (single flop) |

With `=`, `q1` takes `d` immediately, `q2` then reads the *new* `q1`, both flops end up
holding the same value every cycle, and the optimiser deletes the redundant one. **One
character, half the hardware, and a design that is off by a cycle.**

**The nastiest part is that it is not always wrong.** Blocking assignments in a clocked block
can produce correct hardware — sometimes deliberately, if you order the statements to build
the chain you want. That is what makes it dangerous: it fails intermittently and subtly
rather than loudly, and it can pass simulation on your machine and fail on the regression
server. **Follow the rule mechanically; do not reason case by case.**

**Canonical reference:** Clifford Cummings, *"Nonblocking Assignments in Verilog Synthesis,
Coding Styles That Kill!"*, SNUG 2000. Note `sunburst-design.com` now 301-redirects to
`paradigm-works.com`, which serves a catalogue page rather than the PDFs; the papers are
widely mirrored elsewhere. See §8.

### 2.4 `always_comb`, `always_ff`, `always_latch`

Verilog has one `always` keyword for three completely different kinds of hardware.
SystemVerilog splits it into three, and the split is the point: **the new keywords let you
state your intent so the tool can check it.**

```systemverilog
always_comb begin              // I assert: pure combinational, no state
  case (op)
    2'b00: y = a & b;
    2'b01: y = a | b;
    2'b10: y = a ^ b;
    2'b11: y = ~a;
  endcase
end

always_ff @(posedge clk or negedge rst_n) begin   // I assert: flip-flops
  if (!rst_n) q <= '0;
  else        q <= d;
end

always_latch begin             // I assert: yes, I really do want a latch
  if (en) q = d;
end
```

What they buy over plain `always`:

- **`always_comb`** infers its own sensitivity list from everything read in the block, so the
  incomplete-sensitivity-list bug (§2.6) becomes impossible. It **errors if the block would
  infer a latch**, and forbids anything else from assigning the same variables. It also
  executes once at time zero, so combinational outputs are settled before the first clock.
- **`always_ff`** requires a clock edge in the sensitivity list and errors if the block would
  produce combinational logic or if another block drives the same signal.
- **`always_latch`** documents a deliberate latch, so reviewers and tools know it was not an
  accident.

**This is the single highest-leverage habit to teach.** Two entire bug classes — inferred
latches and incomplete sensitivity lists — become compile-time errors rather than
silicon-time mysteries, for free, by using a more specific keyword. There is no reason to
write bare `always` in new code.

Verilator, Icarus and Yosys all accept these; HDLBits' Icarus backend accepts them but its
problem set does not exercise them (§0.5).

### 2.5 Inferred latches — how they happen and why they are almost always a bug

**The mechanism.** In a combinational block, if there is **any path through the code that
does not assign a value to an output**, that output must *remember* its previous value —
because the language says a variable holds its last assigned value. Memory in combinational
logic means a **level-sensitive latch**, and the synthesiser has no choice but to build one.

Two ways to do it, and they are the two most common beginner bugs in the language:

```verilog
// (1) an if with no else
always @* begin
  if (sel) y = a;        // what is y when sel == 0?  -> latch
end

// (2) a case that does not cover every value
always @* begin
  case (op)
    2'b00: y = a & b;
    2'b01: y = a | b;
    2'b10: y = a ^ b;    // 2'b11 unhandled -> latch
  endcase
end
```

**Why it is a bug.** A latch is transparent while its enable is high — data flows straight
through — and holds when it goes low. That means:

- **Timing analysis becomes much harder.** Static timing analysis (§4.4) is built around
  edge-triggered flops; latches introduce time borrowing and multi-cycle paths that most
  flows analyse badly or not at all. **A latch is where timing closure goes to die.**
- **It is usually not what you meant.** You wanted a mux and forgot a branch. The synthesiser
  silently built storage you did not want and did not know about.
- **Glitches propagate.** While transparent, any glitch on the input passes to the output and
  can be captured. Flops sample once per edge and are immune.
- **FPGAs are bad at them.** Fabric is built from flip-flops; latches map awkwardly, cost
  more, and some architectures cannot do them cleanly at all.

**The three fixes**, in order of preference:

1. **Assign a default first**, then override — the most robust habit, immune to later edits
   adding a branch:
   ```systemverilog
   always_comb begin
     y = 1'b0;          // default: every path now assigns y
     if (sel) y = a;
   end
   ```
2. **Make every `if` have an `else` and every `case` have a `default`.**
3. **Use `always_comb`**, which turns the mistake into a compile error rather than a silent
   latch.

**How to spot one in the tools.** Verified against Yosys 0.68 (§0.4(a)):

```
Warning: Latch inferred for signal `\ctrl.\y' from process `\ctrl.$proc$latch.v:2$1': ...
```

plus a `$dlatch` cell in the `stat` report that you did not ask for. Vendor tools say the
same thing in their own dialect — Vivado emits `[Synth 8-327] inferring latch for variable
'y_reg'`; Quartus emits `Warning (10240): Inferring latch(es) for variable "y"`.

**Teach the learner to read the synthesis log, not just the error list.** This is a
*warning*, not an error; a design with inferred latches builds successfully and ships. The
skill being taught is: **warnings in synthesis are not like warnings in a compiler — this one
means your hardware is wrong.**

A related trap: `full_case`/`parallel_case` pragmas, and SystemVerilog's `unique`/`priority`
case qualifiers, suppress latch inference by *promising* the tool something. `unique case` is
checkable and reasonable; the old `// synopsys full_case` pragma is a notorious source of
simulation/synthesis mismatch, because it makes synthesis assume something simulation does
not. Mention it as a thing to recognise and avoid.

### 2.6 Sensitivity lists and the classic bug

The old form names its wake-up signals explicitly:

```verilog
always @(a or b) y = a & b & c;   // BUG: c is missing
```

In **simulation** the block only re-runs when `a` or `b` change. A change on `c` alone does
nothing, and `y` is stale — behaving like a latch that never opens.

In **synthesis** the tool ignores the sensitivity list entirely and builds a 3-input AND gate
from the expression. So the gates are right and the simulation is wrong: the canonical
**simulation/synthesis mismatch**. You debug a "working" design that fails in hardware, or
worse, "fix" hardware to match a broken simulation.

Fixes in order: **`always_comb`** (infers the list, cannot be wrong); **`always @*`**
(Verilog-2001, infers the list, but does not check for latches and misses signals read only
inside function calls in some tools). **Never hand-write a combinational sensitivity list.**

Note the asymmetry that makes this confusing to explain: for **combinational** blocks the
sensitivity list is a simulation artefact synthesis ignores. For **sequential** blocks
`@(posedge clk)` is load-bearing — it is *the* thing that tells the synthesiser to build a
flip-flop, and `posedge` vs `negedge`, and the presence of `or negedge rst_n`, directly
determine the hardware (§4.6).

### 2.7 Parameters and generate

Parameters are compile-time constants — the mechanism for reuse without duplication.
`parameter` is overridable at instantiation; `localparam` is not (use it for derived
constants and state encodings).

```systemverilog
module fifo #(
  parameter int WIDTH = 8,
  parameter int DEPTH = 16,
  localparam int AW   = $clog2(DEPTH)
) ( ... );
```

`generate` builds **structure** at elaboration time — the loop variable is a compile-time
index, and each iteration creates real, distinct hardware:

```systemverilog
genvar i;
generate
  for (i = 0; i < WIDTH; i = i + 1) begin : g_bit
    full_adder u_fa (.a(a[i]), .b(b[i]), .cin(c[i]), .sum(sum[i]), .cout(c[i+1]));
  end
endgenerate
```

That is a ripple-carry adder of `WIDTH` physically distinct full adders wired in a chain —
the direct Verilog translation of what Part 0 built by hand in `Add16.hdl`. **Use this as the
bridge exercise:** the Part 0 learner wrote sixteen instantiations; `generate` writes them
for you, and the hardware is identical. It makes "the loop is in the compiler, not the chip"
concrete.

`generate if`/`case` select between structural variants at compile time (e.g. pick a fast
carry-lookahead adder above some width). Note the naming convention `begin : g_bit` — named
generate blocks produce predictable hierarchical names in the netlist, which matters
enormously when reading a waveform or writing a timing constraint.

### 2.8 The synthesisable subset vs. simulation-only constructs

**This confuses beginners more than any other single thing about the language, because the
compiler does not enforce it.** Verilog is one language covering two jobs, and only about
half of it can become hardware.

| Simulation only | Synthesisable |
|---|---|
| `initial` blocks | `always_ff`, `always_comb` |
| `#10` delays, `wait` | clock-edge sensitivity |
| `$display`, `$monitor`, `$finish` | — |
| `$random`, constrained random | — |
| `real`, `time`, strings | `logic`, packed arrays, structs |
| classes, `mailbox`, `semaphore` | — |
| `force` / `release` | — |
| file I/O (`$fopen`, `$readmemh`†) | — |
| dynamic arrays, queues | fixed-size arrays |

† `$readmemh` is the exception that proves the rule: most FPGA tools *do* accept it to
initialise block RAM contents, because the bitstream can carry initial memory state. On an
ASIC it is meaningless — RAM comes up undefined. A good example of "the subset is defined by
the target, not the language."

**Why beginners trip.** `initial` looks exactly like a constructor or a `main`. It is
neither. On an FPGA, `initial` values for flops *are* honoured (the bitstream sets them at
configuration), which teaches a habit that breaks the day the learner targets an ASIC or a
different FPGA family. **Teach an explicit reset from day one** and treat `initial` as
testbench-only, no exceptions.

The deeper point, worth stating plainly: **the synthesisable subset is not defined by the
IEEE standard.** It is defined by what your synthesiser happens to support, which varies by
tool and version. IEEE 1364.1 tried to standardise it and is largely ignored. In practice
"synthesisable" means "Vivado/Quartus/Yosys accepted it", which is why designers converge on
a small, conservative, well-understood coding style rather than exploring the language. That
conservatism is a feature, and it is worth telling learners the industry deliberately uses
maybe 20% of Verilog for design and a different 40% for verification.

### 2.9 VHDL, contrasted briefly

VHDL (IEEE 1076, Ada-derived, from the US DoD VHSIC program) is the other major HDL. Same
concepts, different temperament:

- **Strong, explicit typing.** No implicit width conversion; `std_logic_vector` to `unsigned`
  to `integer` all require explicit conversion functions. Verilog will silently truncate or
  zero-extend a mismatched width and say nothing.
- **Verbose.** Entity/architecture split, `signal`/`variable` distinction, `process` blocks,
  explicit library and `use` clauses. A module that is 10 lines of SystemVerilog is 30 of
  VHDL.
- **The trade is real.** VHDL catches at compile time a large class of bugs Verilog lets
  through to simulation — width mismatches above all. Verilog gets you to a running
  simulation faster and lets you shoot yourself.
- **`signal` vs `variable` is VHDL's `<=` vs `=`.** `signal` assignment (`<=`) is scheduled
  and takes effect at the end of the process — the same deferred-update semantics as
  Verilog's non-blocking. `variable` assignment (`:=`) is immediate, like blocking. The same
  conceptual split, expressed in the type system rather than the operator, which is arguably
  the better design.

**Where it is still dominant:** Europe generally, aerospace and defence, rail and other
safety-critical/certified domains, and a good deal of academia. Altera/Intel's ecosystem has
historically leaned VHDL more than AMD/Xilinx's.

**Current position:** SystemVerilog has clearly won verification everywhere (UVM is
SystemVerilog) and dominates design in the US and Asia. Modern flows are frequently
mixed-language. **For this curriculum: teach SystemVerilog, and give VHDL one honest page** so
the learner can read it and knows why a job posting might demand it. GHDL is the open-source
VHDL simulator, and Yosys can read VHDL via the `ghdl-yosys-plugin`.

### 2.10 The modern generator approach: Chisel, Amaranth, SpinalHDL

A different bet: rather than a special-purpose language with awkward compile-time
metaprogramming bolted on (`generate`), **embed hardware construction in a real
general-purpose language.** Your "HDL code" is a *program that runs* and whose *output* is a
netlist. Loops, functions, type classes, unit tests and package managers come free because
they are the host language's.

- **Chisel** (Scala, UC Berkeley). Emits FIRRTL, now lowered by the **CIRCT** MLIR toolchain
  (the same CIRCT that is the sole HDL-adjacent entry on Compiler Explorer, §0.1) to Verilog.
  Used for the RISC-V Rocket Chip and BOOM cores, and in production at SiFive. The most
  industrially proven of the three.
- **Amaranth** (Python; formerly nMigen). Verified from its docs: "a Python library for
  register transfer level modeling of synchronous logic" — explicitly a generator/embedded
  DSL, not an HDL. Ships a **language, a standard library** (CDC primitives, FIFOs, I/O), an
  **event-driven Python simulator** supporting multiple clocks and async resets, and a
  **build system** with FPGA toolchain integration and board definitions. Emits
  human-readable Verilog for industry tools and can drive Yosys directly. Its stated design
  goal is being "not only easy to use, but also hard to accidentally misuse" — it removes
  non-synthesisable constructs and error-prone inference by construction.
- **SpinalHDL** (Scala). Similar to Chisel, generally regarded as having a cleaner API and
  more readable generated Verilog. Emits both Verilog and VHDL.

**What they buy:** parameterisation that is just ordinary code; strong static typing over
bundles and interfaces; genuine libraries and dependency management; testbenches in a
language with real data structures; and, critically, **whole classes of bug made
unrepresentable** — Amaranth will not let you infer a latch or write an incomplete
sensitivity list, because those constructs do not exist in it.

**What they cost:** another language on top of Verilog (you still must read the generated
Verilog when debugging, and it is machine-written); a smaller community; and tool friction —
vendor timing, formal and DFT flows all speak Verilog, and error messages come back in terms
of generated names.

**For the curriculum: teach Verilog/SystemVerilog first.** It is what the tools, the
literature and the jobs use, and you cannot debug generated Verilog you cannot read.
Introduce Amaranth *after* the Verilog units as a "here is what this could look like"
capstone — it is Python, which the learner already has, and its built-in simulator and build
system make it the lowest-friction path from source to an actual FPGA bitstream.

## 3. Simulation and verification — where the hours actually go

**Say this plainly and early: on a real chip project, verification consumes more time,
more engineers and more compute than design.** Industry surveys have put verification
engineers at parity with or outnumbering design engineers on ASIC projects for over a
decade, and roughly half of project time goes to verification with a substantial fraction
of tapeouts still requiring a respin for functional bugs. A learner who thinks
"digital design" means "writing RTL" has the wrong picture of the job by a factor of two.

This matters pedagogically: **the fun part is writing the CPU; the actual skill is proving
it works.** Part 0's test scripts gave a hint of this. This section is where it becomes the
main event.

### 3.1 Event-driven simulation and the delta cycle

A Verilog simulator is a program pretending to be a parallel circuit. The machinery:

1. An **event queue** ordered by simulation time.
2. At each time step, pop all events at that time and execute them, sorted into the
   regions of §2.3 (Active → Inactive → NBA → Observed → Reactive).
3. Executing an event may **schedule new events at the same simulation time** — a gate
   output changed, so everything downstream must re-evaluate.
4. Repeat step 2 until no events remain at this time. **Only then** advance time.

Those repeated same-time iterations are **delta cycles**: zero simulation time elapses, but
causality is preserved and ordering is well-defined. A combinational cloud 10 gates deep
settles over ~10 delta cycles, all at the same `$time`. This is how the simulator
reconciles "everything is concurrent" with "I am a single-threaded program."

Two payoffs from teaching this properly:

- **The `<=` rule stops being arbitrary.** The NBA region is a specific place in this loop
  (§2.3), and once you can see the loop you can see why the rule works.
- **You can explain "delta cycle" hangs.** A combinational loop (`assign a = ~a;`) never
  settles; the simulator spins forever generating delta cycles at the same timestamp. Real
  hardware would be a ring oscillator. Same bug, two symptoms.

SystemC (available in-browser, §0.3) implements the same model — `sc_signal` writes become
visible in the next delta cycle, which is why that verified `1 edge: b=171 c=0` output is
a legitimate demonstration of the concept.

### 3.2 Testbenches: stimulus, golden model, self-checking

A testbench is a module with no ports that instantiates the design under test (DUT),
drives its inputs and checks its outputs. Three levels of maturity, and the curriculum
should march the learner up them deliberately:

**Level 1 — eyeball.** Drive some inputs, `$display` some outputs, look at the log or the
waveform. Fine for the first ten minutes, useless beyond that: it does not scale, it does
not regress, and "it looked right" is not a result.

**Level 2 — self-checking against expected values.** The testbench knows what should
happen and says so:

```systemverilog
module tb_alu;
  logic [7:0] a, b, y;  logic sub;
  logic [7:0] expected;
  int errors = 0;

  alu dut (.a(a), .b(b), .sub(sub), .y(y));

  task check(input [7:0] ta, tb_, input tsub);
    a = ta; b = tb_; sub = tsub;
    expected = tsub ? ta - tb_ : ta + tb_;
    #1;
    if (y !== expected) begin
      $display("FAIL: a=%0d b=%0d sub=%0d -> y=%0d expected=%0d", ta, tb_, tsub, y, expected);
      errors++;
    end
  endtask

  initial begin
    for (int i = 0; i < 256; i++)
      for (int j = 0; j < 256; j++)
        begin check(i[7:0], j[7:0], 1'b0); check(i[7:0], j[7:0], 1'b1); end
    if (errors == 0) $display("PASS: all vectors OK");
    else             $display("FAIL: %0d errors", errors);
    $finish;
  end
endmodule
```

Note `!==` not `!=`: the 4-state comparison, which catches `x` and `z`. Using `!=` here
means an all-`x` output compares "not unequal" and the test passes on garbage. This is a
real and common testbench bug and worth calling out explicitly.

**Level 3 — golden model.** Rather than recomputing the expected value inline, hold a
reference implementation — in C, C++, Python or high-level SystemVerilog — and compare the
RTL against it on every cycle. This is what Verilator makes natural, because the testbench
*is* C++ and the golden model can be an ordinary C function. For a CPU, the golden model is
an instruction-set simulator, and the check is "after each instruction, do all
architectural registers and memory match?" That is exactly the structure Part 0's CPU
emulator already provides, which makes it an unusually clean handoff.

### 3.3 Verilator — the workhorse

**What it is:** not a simulator but a *compiler*. Verilator's own overview: it "converts
Verilog and SystemVerilog hardware description language (HDL) designs into a C++ or
SystemC model", generating `.cpp`/`.h` which you compile and link against your own C++
testbench and a small runtime.

**Why it is fast.** Its documentation is explicit about the mechanism: "Most simulators
must comply with the complete IEEE 1364 (Verilog) and IEEE 1800 (SystemVerilog) standards,
meaning they have to be event-driven. This prevents them from being able to reorder blocks
and make netlist-style optimizations." Verilator declines that constraint. It flattens the
design, statically schedules evaluation order, and emits straight-line C++. No event queue
at runtime, no dynamic scheduling, no per-signal callbacks. Order-of-magnitude speedups
over interpreted event-driven simulators are routine, and it multithreads. It is fast
enough to boot Linux on a simulated RISC-V core — which is how a great deal of open-source
CPU work is actually done.

**Its limitations, from the documentation, verified:**

- **"Verilator is mostly a two-state simulator, not a four-state simulator."** No proper
  `x` propagation. Uninitialised-register bugs that a 4-state simulator would flag as `x`
  spreading through your design will simply be some definite value. Partial mitigations
  exist — `--x-assign` and `--x-initial` randomise, so running with different seeds
  surfaces initialisation dependence — but it is a mitigation, not equivalence. **This is
  the limitation that matters most and is most often glossed over.**
- **Timing needs opting in.** Delays, event controls, intra-assignment timing, net delays,
  `wait` and `fork` require the `--timing` flag, which itself **requires C++20 coroutine
  support**. Without it these are a `NOTIMING` error (delays instead give a `STMTDLY`
  warning). So `#10`-style testbenches do not work out of the box; Verilator testbenches
  are naturally written as explicit C++ clock toggling.
- **Synthesis subset.** It "supports the Synthesis subset with other verification
  constructs being added over time", and evaluates events roughly as Synopsys Design
  Compiler would.
- **Class support is "limited but in active development"** — members, methods, extension,
  parameters. **This is why Verilator does not run UVM**, which depends heavily on classes,
  randomisation and the full object model.
- Limited VPI, partial PLI (`$display`, `$finish`, `$stop`, `$time`, `$write` are
  converted to C++). VCD and FST tracing are supported.

**When to reach for it:** simulating synthesisable RTL fast, regression suites, C++ golden
models, anything CPU-sized. **When not to:** gate-level netlists with timing, X-propagation
and reset-verification work, UVM environments, mixed-signal.

### 3.4 Icarus Verilog and the open-source flow

**Icarus Verilog (`iverilog`)** is a true event-driven, 4-state, interpreting simulator.
Slower than Verilator by a wide margin, but it does the things Verilator will not: proper
`x`/`z`, delays without ceremony, `initial` blocks, `$display` and `#` timing exactly as a
beginner expects. Coverage of Verilog-2005 is good; SystemVerilog support is partial and
improving.

**For a beginner course, Icarus is the better first simulator** — it accepts textbook
testbench style with no flags, and it is what HDLBits runs behind the scenes (§0.5), so
what a learner writes on HDLBits is what they can run locally. Introduce Verilator later,
when speed and C++ golden models start to matter.

Typical open-source loop:

```
iverilog -g2012 -o sim tb_alu.sv alu.sv   # compile
vvp sim                                    # run, prints PASS/FAIL, writes dump.vcd
gtkwave dump.vcd                           # look at it
```

Versus Verilator:

```
verilator --cc --exe --build --trace alu.sv sim_main.cpp
./obj_dir/Valu
```

**Also in the ecosystem:** GHDL (VHDL), cocotb (write testbenches in **Python**, driving
Icarus/Verilator/commercial sims via VPI — a genuinely good fit for a curriculum where the
learner already knows Python), and Surfer (a modern waveform viewer, including a
browser-based build).

### 3.5 Waveforms, VCD/FST, and reading one as a skill

**VCD** (Value Change Dump) is the IEEE-standard, plain-text, universally supported format.
It is also enormous — a long simulation of a large design produces gigabytes. **FST** (Fast
Signal Trace, from GTKWave) is a compressed binary alternative, dramatically smaller and
faster to open; Verilator supports both (`--trace` / `--trace-fst`).

```verilog
initial begin
  $dumpfile("dump.vcd");
  $dumpvars(0, tb_alu);   // 0 = all levels of hierarchy below this scope
end
```

**Reading a waveform is a distinct, learnable, teachable skill, and it is the primary
debugging tool of the entire field.** It deserves explicit instruction — most courses just
show a screenshot and move on. What to actually teach:

- **Find the first cycle where reality diverges from expectation, then work backwards.** A
  bug 400 cycles in usually originates from something wrong 3 cycles in. Bisect in time.
- **Read edges, not levels.** Line the cursor up on a clock edge and ask what each flop
  sampled *just before* it. This is the visual form of the `<=` rule and it makes §2.3
  click for people who did not get it from prose.
- **`x` is information.** A red/`x` signal means undriven, uninitialised, or multiply
  driven. Trace it upstream to its source. Propagating `x` is a gift — it points at the bug.
- **`z` means nobody is driving.** Usually a tri-state bus with no enable asserted, or a
  forgotten connection. Part 0's Hack platform had no tri-state, so this will be new.
- **Look at control before data.** If a datapath value is wrong, the enable, select or
  valid signal that steered it is wrong more often than the arithmetic.
- **Add the state register to the top of the view.** For an FSM, watching the state
  encoding transition is usually enough to localise the bug without looking at anything
  else.
- **Group and order signals deliberately.** A waveform with 200 unordered signals is
  unreadable; the same 200 grouped by module and ordered by pipeline stage is obvious.

For the Part 0 CPU reimplementation, the exercise writes itself: dump a waveform of the
CPU executing a known program and have the learner **annotate the fetch/decode/execute
phases from the waveform alone**. This also repairs the specific gap noted in §1.7 — the
Hack CPU is single-cycle, so the learner has never *seen* an instruction take time.

### 3.6 Assertions and SVA

An assertion is an executable statement of intent embedded in the design, checked
continuously by the simulator. The great advantage over testbench checking: **an assertion
fires at the site and moment of the violation**, not three modules downstream when a wrong
value finally reaches an output you happened to be checking.

**Immediate assertions** are procedural, like a software `assert`:

```systemverilog
always_comb
  assert (!(read_en && write_en))
    else $error("read and write asserted simultaneously");
```

**Concurrent assertions** are temporal — they describe behaviour *over time*, sampled on a
clock, and this is where SVA earns its keep:

```systemverilog
// req must be followed by ack within 1 to 4 cycles
property p_req_ack;
  @(posedge clk) disable iff (!rst_n)
    req |-> ##[1:4] ack;
endproperty
assert property (p_req_ack);

// a one-hot state encoding must stay one-hot
assert property (@(posedge clk) disable iff (!rst_n) $onehot(state));

// FIFO must never overflow
assert property (@(posedge clk) disable iff (!rst_n) !(full && push));
```

Vocabulary worth teaching: `|->` (overlapping implication — check the consequent starting
this cycle), `|=>` (non-overlapping — start next cycle), `##n` (delay), `##[1:4]` (window),
`$rose`/`$fell`/`$stable`/`$past` (edge and history functions), `disable iff` (suppress
during reset — omitting this is the single most common SVA mistake, since everything looks
broken during reset).

Three roles, and the third is the one that surprises people:

- `assert` — must always hold; the tool reports a violation.
- `assume` — a constraint on the *environment*, telling a formal tool what inputs are
  legal. Ignored-ish in simulation, load-bearing in formal.
- `cover` — not a check but a **question**: "did this situation ever occur?" A cover
  property that never fires means your tests never exercised that case, which is often
  more alarming than a failing assert.

Assertions are the natural bridge to §3.9, because the *same* SVA text can be checked by
simulation and **proved** by a formal tool.

### 3.7 Constrained-random verification and UVM, in outline

**The problem with directed tests:** you only find bugs you thought to look for. A 32-bit
adder has 2^64 input pairs; you cannot enumerate them, and hand-picked corners miss the
ones you did not imagine.

**Constrained random** generates legal-but-arbitrary stimulus:

```systemverilog
class packet;
  rand bit [7:0]  len;
  rand bit [31:0] addr;
  rand bit        is_write;
  constraint c_len  { len inside {[1:64]}; }
  constraint c_addr { addr % 4 == 0; addr < 32'h1000_0000; }
endclass
```

The solver produces random values satisfying the constraints. Run it for millions of
cycles, check with a scoreboard and assertions, and let the machine explore corners you
would never have written down. This is *the* dominant industrial methodology, and its
effectiveness depends entirely on **functional coverage** (§3.8) to tell you what the
randomness actually reached.

**UVM (Universal Verification Methodology)** is the Accellera-standardised SystemVerilog
class library that industrialises this. The architecture, in outline:

- **Sequence items** — transactions. **Sequences** — streams of them. **Sequencer** —
  arbitrates and delivers.
- **Driver** — converts transactions into pin wiggles. **Monitor** — the reverse, observing
  pins and reconstructing transactions.
- **Agent** — driver + monitor + sequencer for one interface. **Environment** — agents plus
  scoreboards. **Test** — configures the environment and starts sequences.
- Plus a factory for type overriding, a configuration database, TLM ports, and phased
  execution (build, connect, run, check, report).

**And now the honest note, which the brief rightly asked for.** UVM is industrial-scale
machinery. A minimal "hello world" UVM testbench is several hundred lines across a dozen
files before it checks anything at all. It is designed for teams of verification engineers
building reusable environments for multi-million-gate chips over multi-year projects, and
in that context the investment pays back many times over. **For an individual learner
verifying a small CPU it is enormous overkill**, and worse, learning UVM tends to teach the
framework rather than the underlying ideas. It also **does not run on Verilator** (§3.3 —
class support is limited), so it requires a commercial simulator, which prices it out of a
self-directed curriculum entirely.

**Recommendation: teach the underlying concepts — transactions, drivers, monitors,
scoreboards, constrained random, coverage — using plain SystemVerilog or cocotb, and
describe UVM in two pages so the learner recognises it and knows what a job posting means.
Do not attempt to teach UVM.** The concepts transfer; the boilerplate does not, and it is
learnable on the job in a week once the concepts are solid.

### 3.8 Coverage-driven verification

Random stimulus is only useful if you know what it reached. Two kinds:

- **Code coverage** — automatic, mechanical. Line, branch, toggle (did each bit go both
  0→1 and 1→0?), FSM state and arc coverage, expression/condition coverage. Easy to
  collect, and a weak signal: 100% code coverage says every line ran, not that anything
  was correct or that any interesting *combination* occurred.
- **Functional coverage** — hand-written, meaningful. You declare what situations matter:

```systemverilog
covergroup cg_alu @(posedge clk);
  cp_op   : coverpoint op { bins ops[] = {[0:15]}; }
  cp_zero : coverpoint (result == 0);
  cp_ovf  : coverpoint overflow;
  cross cp_op, cp_zero, cp_ovf;    // every op x zero x overflow combination
endgroup
```

That `cross` is the point: it asks not "did each thing happen" but "did every *combination*
happen." Functional coverage is where the design intent gets written down in checkable
form, and writing good coverage models is a genuine skill.

**The loop, which is the actual methodology:** write constraints → run random → measure
coverage → find holes → tighten or add constraints to reach them → repeat until coverage
closes. "Coverage closure" is a real project milestone with real schedule attached.
Coverage plus assertions is the industrial answer to "how do you know you are done", and it
is an honest answer as far as it goes — which is not all the way, hence §3.9.

### 3.9 Formal property verification and equivalence checking

Simulation samples the input space. **Formal proves over all of it.** Rather than running
vectors, a formal tool converts the design and its assertions into a mathematical problem
and hands it to a SAT or SMT solver.

Two distinct activities:

**Formal property verification (FPV)** — prove assertions hold for *every* reachable state
and *every* legal input, or produce a concrete counterexample trace. Techniques:

- **BMC (bounded model checking):** "no violation within N cycles from reset." Fast,
  always terminates, but only bounded — a bug at cycle N+1 is invisible.
- **k-induction / unbounded proof:** if the property holds for k consecutive cycles and
  holding for k implies holding for k+1, it holds forever. Gives a real proof, but may
  need auxiliary invariants to get there.
- **Cover:** ask the solver to *reach* a state, producing a trace that gets there. A
  superb way to generate interesting test cases you did not think of, and to sanity-check
  that your assumptions have not accidentally made the design unreachable.

**Equivalence checking** — prove two designs are functionally identical. Combinational
equivalence (RTL vs. synthesised netlist) is routine industrial practice and runs on
essentially every tapeout: it is how you trust the synthesiser. Sequential equivalence
(pre- vs. post-retiming, or two different microarchitectures) is harder but tractable.

**The open-source flow: SymbiYosys (`sby`)**, verified from its documentation as "a
front-end driver program for Yosys-based formal hardware verification flows." It provides
bounded verification of safety properties, unbounded verification, testbench generation
from cover statements, and liveness verification. Engines include `smtbmc`, `btor`,
`aiger`, `abc` and `itp`, backed by solvers such as Yices, Z3, Boolector/Bitwuzla and ABC.
It accepts Verilog with formal extensions, SystemVerilog including concurrent and immediate
assertions and a supported subset of SVA property syntax, and VHDL via GHDL.

**And, verified in §0.4(c): you do not even need `sby` to start.** Yosys' own built-in SAT
solver did a full equivalence proof of an 8-bit ALU against a golden model — `SAT proof
finished - no model found: SUCCESS!` — and produced a concrete counterexample (`a=214,
b=199`) when the design was broken. **That runs today from a single `pip install
yowasp-yosys`, with no SMT solver, no license and no C++ toolchain.**

This is worth dwelling on pedagogically. Part 0's ALU was checked with a test script that
sampled some vectors. Here the learner can **prove** their ALU correct for all 2^17 input
combinations in milliseconds. That is a qualitative upgrade in what "verified" means, it is
the kind of thing that is genuinely exciting the first time, and it is uniquely achievable
in hardware — the state space is finite, which is exactly why formal works here and remains
a research problem for software.

**Honest limits:** formal explodes on large state spaces (wide counters and deep memories
are murder — the standard trick is to shrink the design's parameters for the proof);
writing good properties is harder than writing tests; and a proof is only as good as your
`assume` constraints — over-constrain and you prove something vacuously, which is why
`cover` sanity checks matter. Formal complements simulation, it does not replace it.

### 3.10 Where the hours go — the summary to give the learner

| Activity | Rough share of effort |
|---|---|
| Writing RTL | small |
| Writing testbenches, models, checkers | large |
| Debugging simulation failures | large |
| Coverage closure | significant |
| Timing closure (§4) | significant |
| Everything else | the rest |

The line worth saying out loud: **"You will spend more time proving the CPU works than
building it, and that ratio is normal, permanent, and the reason hardware engineers are
paid."** Part 0 could hide this because its designs were small and its test scripts were
handed to you. Here the learner writes the tests, and finds out.

## 4. Synthesis and the physical reality

### 4.1 The flow, end to end

```
  RTL (SystemVerilog)
        |  elaboration: resolve parameters, unroll generate, build hierarchy
        v
  Technology-independent netlist        (generic AND/OR/MUX/DFF; Yosys calls this RTLIL)
        |  logic optimisation: constant propagation, common subexpression,
        |  FSM re-encoding, resource sharing, Boolean minimisation
        v
  Optimised generic netlist
        |  TECHNOLOGY MAPPING  <-- the target-specific step
        v
  Technology netlist    (FPGA: LUTs, FFs, BRAM, DSP  |  ASIC: standard cells from a library)
        |
        v
  PLACE  (where does each cell physically go?)
        |
        v
  ROUTE  (which metal wires connect them?)
        |
        v
  Timing analysis / verification / DRC
        |
        v
  BITSTREAM (FPGA)          or          GDSII (ASIC)
```

The step worth dwelling on is **technology mapping**, because it is where the same RTL
becomes two utterly different things. Mapping a 4-input Boolean function to an ASIC means
choosing gates from a standard cell library. Mapping it to an FPGA means stuffing its truth
table into a lookup table (§5.1). The RTL is identical; the physics is not.

**The learner can watch this happen.** With `yowasp-yosys` (§0.4), `synth -top foo; stat`
after each pass shows generic cells becoming `$_DFF_P_`, `$_MUX_`, `$_AND_`; adding
`synth_ice40` maps them to `SB_LUT4` and `SB_DFF`. Making that transition visible is a good
exercise and costs nothing.

### 4.2 What the synthesiser infers

Synthesisers pattern-match idioms. Write the idiom and you get the dedicated hardware; write
something slightly different and you get a pile of LUTs, or nothing.

| You write | You get |
|---|---|
| `a + b` | a carry-chain adder (FPGA: dedicated carry logic, ~free) |
| `a * b` | a **DSP slice** (§5.5) if it fits, else a large LUT multiplier |
| `sel ? a : b` | a multiplexer |
| `always_ff` with `<=` | flip-flops |
| a 2-D array read/written on a clock edge, one port | **block RAM** |
| the same array with async read | **distributed RAM** (LUTRAM) or registers |
| `case` on a state register | an FSM, possibly re-encoded (binary → one-hot) |
| a shift register with no taps | an **SRL32** shift-register LUT on Xilinx |
| `a % 8`, `a / 4` (power of two) | free — just wire selection |

**What it will refuse, or do badly:**

- **Division and modulo by a non-constant.** Enormous, slow, or rejected outright. You must
  instantiate an IP core or build a multi-cycle algorithm.
- **Floating point.** No inference at all; you instantiate IP.
- **Loops with non-constant bounds**, unbounded recursion, dynamic memory. Not
  representable in fixed silicon.
- **Multiple drivers** on one signal, or a signal driven from two `always` blocks.
- **Combinational loops.** Rejected; there is no stable value.
- **`initial` on an ASIC** (§2.8).
- **Asynchronous logic**, delay lines, anything relying on gate delay for correctness. Every
  synthesis flow assumes synchronous design; deliberate asynchronous logic requires a
  different methodology entirely.

**The inference rules are tool- and target-specific and are documented in vendor coding
guides.** The practical lesson: **memory and DSP inference is fragile.** A block RAM
inferred on one tool becomes 4,000 LUTs on another because you added an asynchronous read or
a reset the primitive does not support. Always check the utilisation report against what you
expected — this is a habit, not an occasional check. "It synthesised" and "it synthesised to
what I intended" are different claims.

### 4.3 The utilisation report is the new compiler output

In software, compilation either succeeds or fails. In hardware, synthesis nearly always
"succeeds" and hands you a **resource report** that is the real result:

```
Slice LUTs      : 3,412 / 20,800  (16%)
Slice Registers : 2,109 / 41,600  ( 5%)
Block RAM Tile  :    12 / 50      (24%)
DSPs            :     4 / 90      ( 4%)
```

Teach the learner to read this the way they read a profiler. Numbers wildly above
expectation mean a failed inference (a multiplier that became LUTs, a RAM that became flops).
This is the direct answer to Part 0's "a chip was free" (§1.7).

### 4.4 Static timing analysis — the fundamentals

**This is the concept that most distinguishes hardware from software, and it has no software
analogue at all.** A software function that is slow is slow. A circuit that is too slow is
**wrong** — it produces incorrect values, not late ones.

**The physical picture.** Data leaves a flip-flop, propagates through combinational logic,
and must arrive at the next flip-flop's input and be **stable** for a window around the next
clock edge. If it arrives late, the capturing flop samples a value that is still changing and
latches garbage.

**The four quantities:**

- **t_cq (clock-to-Q):** delay from the clock edge until the launching flop's output is
  valid. The flop is not instantaneous.
- **t_comb (combinational delay):** propagation through the logic between the two flops. The
  part you control by writing better RTL.
- **t_setup:** how long the data must be stable *before* the capturing clock edge.
- **t_hold:** how long the data must remain stable *after* the capturing clock edge.

**The setup equation** — the one to memorise:

```
    T_clk  >=  t_cq + t_comb(max) + t_setup + t_skew
```

Read it as: one clock period must be long enough for the signal to get out of the first flop,
across the logic, and settle before the next edge. Rearranged:

```
    Fmax = 1 / (t_cq + t_comb(max) + t_setup + t_skew)
```

**Slack** is the margin:

```
    setup slack = T_clk - (t_cq + t_comb + t_setup + t_skew)
```

**Positive slack: passes. Negative slack: fails.** The tool reports the worst path in the
design (Worst Negative Slack, WNS) and the sum over all failing paths (Total Negative Slack,
TNS). "Timing closure" means driving WNS to ≥ 0 across every path, every corner.

**The critical path** is the longest combinational path between any two registers. It alone
determines Fmax — a design with one 12 ns path and ten thousand 2 ns paths runs at 83 MHz.
Optimising anything but the critical path is wasted effort, which makes this **exactly
analogous to Amdahl's law and profiling**, and worth drawing that parallel explicitly for a
learner coming from software.

**Hold violations are different and worse.** The hold check is:

```
    t_cq + t_comb(min)  >=  t_hold + t_skew
```

Note what is *absent*: **T_clk does not appear.** A hold violation is data arriving *too
early* — racing through short logic and corrupting the capture of the *previous* value. So
**you cannot fix a hold violation by slowing the clock down.** It is a broken circuit at any
frequency. Fixes mean adding delay (buffers) or fixing clock skew. On an FPGA the tools
almost always fix hold automatically; on an ASIC it is a real and painful part of the flow.
This asymmetry — setup is fixable by slowing down, hold is not — is the single most useful
thing to know about timing and is routinely omitted from tutorials.

**Why timing closure is the hard part.** It is the hardware equivalent of a performance
regression that fails the build, with several compounding difficulties:

1. **It appears late.** You only learn the real number after place-and-route, minutes to
   hours after you wrote the code.
2. **It is non-local.** The critical path may run through five modules written by four
   people. No one owns it.
3. **Fixing one path creates another.** Pipelining the worst path makes something else the
   worst path. Progress is genuinely iterative.
4. **The tools are stochastic.** Placement uses randomised heuristics; a trivial code change
   can shift timing by several percent in either direction for no semantic reason. This is
   deeply unnerving to someone used to deterministic compilers, and it should be said out
   loud rather than discovered.
5. **Multiple corners.** Slow-process/high-temperature/low-voltage and its opposite must
   *both* pass — the slow corner for setup, the fast corner for hold.

**Constraints are input, not output.** You must *tell* the tool the clock period; it cannot
guess. In SDC (Synopsys Design Constraints), the format every tool speaks:

```tcl
create_clock -name clk -period 10.000 [get_ports clk]     # 100 MHz
set_input_delay  -clock clk 2.0 [get_ports data_in]
set_output_delay -clock clk 2.0 [get_ports data_out]
set_false_path -from [get_clocks clk_a] -to [get_clocks clk_b]
```

**An unconstrained path is not analysed, and therefore always "passes."** A design that
reports 100% timing closure with no constraints file has proved nothing whatsoever. This is a
very common beginner mistake and a good thing to demonstrate deliberately.

### 4.5 Clock domain crossing and metastability

**Metastability.** A flip-flop has a forbidden window — the setup/hold aperture. If its input
changes inside that window, the flop enters a **metastable** state: its output sits at an
invalid intermediate voltage, or oscillates, for an unbounded time before resolving randomly
to 0 or 1. This is not a design error; it is physics. Any flop can be driven metastable, and
in a single clock domain STA's job is precisely to guarantee it never happens.

**Across clock domains, you cannot make that guarantee.** If two clocks are unrelated, some
transition will eventually land in the aperture. It is a certainty, not a risk.

**MTBF.** Metastability resolves exponentially:

```
    MTBF  =  exp(t_r / tau)  /  (T_0 * f_clk * f_data)
```

where `t_r` is the resolution time allowed (roughly one clock period for a two-flop
synchroniser), `tau` is the flop's resolution time constant, `T_0` is a susceptibility
constant, `f_clk` is the sampling clock, `f_data` the rate of asynchronous input changes.

**The argument that matters is the shape, not the numbers:** MTBF is *exponential* in the
resolution time you allow, and only *linear* in the frequencies. So **adding one more flop
stage buys orders of magnitude** of reliability for one flop of area and one cycle of
latency. That is why the standard answer is two flops and why three appear in high-frequency
or safety-critical designs. And note the honest framing: **you are not eliminating failure,
you are buying a mean time between failures measured in millennia.** There is no way to make
it zero, and that is a genuinely different engineering posture from software correctness.

**The two-flop synchroniser** — for a single bit only:

```systemverilog
logic sync_ff1, sync_ff2;
always_ff @(posedge clk_dst or negedge rst_n) begin
  if (!rst_n)  {sync_ff2, sync_ff1} <= 2'b00;
  else         {sync_ff2, sync_ff1} <= {sync_ff1, async_in};
end
assign safe_signal = sync_ff2;
```

`sync_ff1` may go metastable; it is given a full clock period to resolve before `sync_ff2`
samples it.

**The critical limitation, which is the actual lesson: this works for ONE bit and is
catastrophically wrong for a bus.** Each bit's synchroniser resolves independently, so a
counter going `0111 → 1000` can be sampled as *any* of the 16 values while the bits are in
flight. The received value can be one that never existed in the source domain.

**Three correct techniques for multi-bit data:**

1. **Gray code.** Encode so that **exactly one bit changes** between consecutive values. Then
   a mid-flight sample yields either the old value or the new one — never a third. This is
   the foundation of the async FIFO and the reason Gray code appears in this field at all.
   ```
   binary -> gray :   gray = binary ^ (binary >> 1)
   gray -> binary :   binary[MSB] = gray[MSB];
                      binary[i]   = binary[i+1] ^ gray[i]    (descending)
   ```
2. **Handshake.** Sender raises `req` with data held stable; receiver synchronises `req`,
   captures the (stable, hence safe) data, raises `ack`; sender synchronises `ack` and
   drops `req`. Only the two control bits cross asynchronously; the data never does. Simple
   and safe, but slow — four synchroniser latencies per transfer.
3. **Asynchronous FIFO.** The general high-throughput solution, below.

**The asynchronous FIFO with Gray-coded pointers** — the canonical CDC structure and an
excellent exercise:

- A dual-port memory, written in the source domain, read in the destination domain.
- A **write pointer** in the write domain and a **read pointer** in the read domain, each a
  binary counter incremented locally.
- To compute *full* and *empty*, each domain needs the other's pointer. So each pointer is
  **converted to Gray**, passed through a **two-flop synchroniser** into the other domain,
  and compared there. Because Gray changes one bit at a time, a mid-flight sample is either
  the old or the new pointer — never a corrupt one. Worst case you see a *stale* pointer,
  which makes the FIFO look **more full than it is** (write side) or **more empty than it
  is** (read side). Both errors are **conservative and therefore safe** — this is the elegant
  part, and it is worth making the learner articulate why staleness in this direction can
  never cause an overflow or an underflow.
- **The extra-MSB trick.** Pointers are made **one bit wider than the address**. Empty and
  full are then distinguishable:
  - **empty:** read pointer == synchronised write pointer, **all bits equal**.
  - **full:** in Gray, the **top two bits are inverted** and the rest are equal — the Gray
    equivalent of "the pointers differ by exactly the FIFO depth."

  Without the extra bit, full and empty both look like "pointers equal" and are
  indistinguishable.

**Canonical reference:** Clifford Cummings, *"Simulation and Synthesis Techniques for
Asynchronous FIFO Design"*, SNUG 2002 — the standard treatment. Same redirect caveat as
§2.3; see §8.

**CDC bugs are the worst class of hardware bug** and deserve to be named as such: they are
intermittent, temperature- and voltage-dependent, often invisible in simulation (which has no
notion of metastability unless you model it), and they can pass every test and fail in the
field months later. Commercial **CDC linting tools** exist as a separate product category
precisely because of this. The rule to teach: **every signal crossing a clock domain must go
through a reviewed, named synchronisation structure — never a bare wire.**

### 4.6 Resets

**Synchronous reset** — reset is just another synchronous input:

```systemverilog
always_ff @(posedge clk)
  if (rst) q <= '0;
  else     q <= d;
```

Pros: no special timing analysis; filters glitches on the reset line; maps into the FPGA
flop's synchronous reset port. Con: **requires a running clock to take effect.** If the clock
is stopped or not yet locked, the design cannot be reset — which matters at power-up.

**Asynchronous reset** — in the sensitivity list:

```systemverilog
always_ff @(posedge clk or negedge rst_n)
  if (!rst_n) q <= '0;
  else        q <= d;
```

Pros: works with no clock. Con: **de-assertion is the dangerous edge.** If reset releases too
close to a clock edge, the flop can go metastable — the same physics as §4.5. Also a glitch
on the reset line resets the chip.

**The standard answer: asynchronous assert, synchronous de-assert** ("reset synchroniser").
Assert immediately without needing a clock; release synchronously so every flop leaves reset
on the same edge:

```systemverilog
logic rst_meta, rst_sync_n;
always_ff @(posedge clk or negedge rst_n_in) begin
  if (!rst_n_in) {rst_sync_n, rst_meta} <= 2'b00;
  else           {rst_sync_n, rst_meta} <= {rst_meta, 1'b1};
end
```

Note the asymmetry: assertion propagates instantly through the async path; de-assertion walks
through two flops.

**Reset trees.** Reset reaches nearly every flop, so like the clock it is a huge-fanout net
needing a buffer tree and skew management. **Do not reset what you do not have to** — a
pipeline datapath register usually does not need reset (garbage flushes out in a few cycles),
while every control and state register does. On an ASIC, dropping unnecessary resets is a
real area and power saving; on an FPGA, an unnecessary reset can prevent a register from
being packed into a DSP or block RAM, or block SRL inference, silently costing far more than
it appears to.

**One reset domain per clock domain**, each synchronised to its own clock. A reset crossing
domains is a CDC path like any other.

### 4.7 Pipelining and retiming — and the direct link to the architecture units

**The problem:** the critical path is too long, Fmax is too low.

**The fix:** cut the long combinational path by inserting registers, splitting it into
stages. Each stage is shorter, so the clock can be faster. Throughput becomes one result per
cycle at the higher frequency; **latency** in cycles increases, though wall-clock latency
often barely changes.

Before — one 12 ns path, Fmax ≈ 83 MHz:

```systemverilog
always_ff @(posedge clk)
  result <= (a * b) + (c * d);     // multiply and add in one cycle
```

After — two ~6 ns stages, Fmax ≈ 167 MHz, one extra cycle of latency:

```systemverilog
always_ff @(posedge clk) begin
  p1 <= a * b;                     // stage 1
  p2 <= c * d;
  result <= p1 + p2;               // stage 2
end
```

**The costs, which must be stated honestly:** more registers (area and power); more latency;
and — the big one — **control complexity**. Once a datapath has stages, a result computed in
stage 3 may be needed by an instruction in stage 1, and you need **forwarding**. A branch
resolved in stage 4 means stages 1–3 hold instructions that should not execute, and you need
**flushing**. A load whose data is not back yet means **stalls** and hazard detection.

**This is the same material as CPU pipelining in the architecture units, seen from the other
side, and the connection should be made explicit and load-bearing.** The architecture unit
introduces the 5-stage pipeline as a *performance technique* — a way to get more instructions
per second. This unit reveals *why it exists at all*: **the fetch–decode–execute–memory–
writeback split is not primarily a conceptual decomposition, it is a critical-path fix.** The
combinational path from instruction memory through decode through the ALU through data memory
back to the register file is simply too long to run at a competitive clock. Pipeline
registers cut it. Hazards, forwarding and flushing are the *price* paid for that timing fix,
not features of the design.

Say it directly to the learner: **"Every pipeline stage boundary in the CPU you studied is a
place where somebody was failing timing."** That single sentence retroactively explains most
of computer architecture, and it is the strongest reason to place this unit adjacent to the
architecture material.

The Part 0 connection is equally sharp: **the Hack CPU is single-cycle**, so its clock period
must accommodate the *entire* fetch–decode–execute path in one tick. That is precisely why
single-cycle machines are slow, and it is a fact the learner can now compute rather than be
told.

**Retiming** is the automatic version: the tool moves registers backwards or forwards across
combinational logic to balance stage delays, without changing the design's cycle-level
behaviour at its boundaries. Yosys has it; Vivado has it (`-retiming`); it is standard in ASIC
flows. **Register balancing** is the common case — you put three registers at the end of a
long chain and let the tool distribute them to where they do the most good. Retiming does not
change *how many* cycles of latency exist, only *where within the logic* the registers sit.
It cannot invent pipelining you did not ask for.

**Other critical-path fixes**, so the learner has a toolbox rather than one hammer:

- **Restructure the logic.** A balanced adder tree instead of a linear chain: `((a+b)+(c+d))`
  is two levels deep, `(((a+b)+c)+d)` is three.
- **Reduce mux depth.** Deeply nested `if`/`else if` builds a priority chain; a `case` on a
  one-hot select builds a flat mux. Same function, very different depth.
- **Precompute.** Compute both possible results in parallel during the previous cycle and
  select at the end — trading area for depth. (This is exactly what carry-select adders do,
  and what branch prediction does at the architectural scale.)
- **Move logic across a register boundary** — the manual version of retiming.

## 5. FPGA architecture, concretely

An FPGA is a chip full of **programmable logic and programmable wires**. Everything else
follows from that: it is a general-purpose *spatial* computer the way a CPU is a
general-purpose *temporal* one.

### 5.1 The LUT — and what a 6-input LUT actually is

**A lookup table is a truth table stored in SRAM.**

An N-input LUT is a 2^N × 1-bit memory whose address lines are the N logic inputs. Program
the memory with the truth table of the function you want, and the LUT computes it. A 6-input
LUT is **64 SRAM bits and a 64:1 multiplexer tree** — that is the entire mechanism, and it is
worth stating that plainly because the name suggests something more exotic.

The consequence is the key insight of the whole architecture: **a LUT computes any Boolean
function of its inputs, in the same delay, regardless of complexity.** A 6-input XOR, a
6-input majority vote, and a 6-input random function all cost exactly one LUT and one LUT
delay. There is no such thing as a "simpler" function below the LUT granularity. This is
completely alien to the Part 0 gate-counting mindset, where XOR cost more than AND, and it
should be called out as such: **on an FPGA, gate count is the wrong unit. LUT count is the
unit, and Boolean complexity below 6 inputs is free.**

Why 6 inputs? An empirical optimum. Larger LUTs implement more logic per unit but cost
exponentially more SRAM (7-input would be 128 bits) and are slower; smaller LUTs need more
levels and hence more routing, and routing dominates (§5.3). Studies converged on 4–6, and
modern high-end parts use 6.

**Verified against AMD's 7-series CLB documentation (UG474):** the 6-input LUT can be
"configured as either a 6-input LUT with one output, or as **two 5-input LUTs with separate
outputs but common addresses or logic inputs**." That fracturability matters — small
functions do not waste a whole LUT.

### 5.2 Flip-flops, slices, CLBs

Each LUT pairs with flip-flops, and the pair is the atomic unit of FPGA logic. Verified from
UG474 for Xilinx 7-series:

- **A CLB contains a pair of slices** (2 slices per CLB).
- **Each slice contains four 6-input LUTs and eight flip-flops.** Four of the eight flops per
  slice "can optionally be configured as latches."
- **Roughly two-thirds of slices are SLICEL** (logic only); the remainder are **SLICEM**,
  which "can also use their LUTs as distributed 64-bit RAM or as 32-bit shift registers."
- **Dedicated high-speed carry logic** for arithmetic runs vertically through the slice
  (`CARRY4` on 7-series) — this is why `a + b` is cheap and fast while `a * b` is not.
- **SRL32:** SLICEM LUTs can become "32-bit shift registers (SRL32) or two SRL16s". A
  32-deep shift register costs *one LUT* instead of 32 flip-flops — an enormous saving for
  delay lines and FIFOs, and a good example of why FPGA-aware coding beats generic RTL.

Terminology differs by vendor and is a minor but real source of confusion: Xilinx says
**CLB/slice/LUT**, Intel/Altera says **LAB/ALM (Adaptive Logic Module)**, Lattice says
**PLB/slice/LUT4**. Same idea, different words and different arithmetic. Note that the small
iCE40 parts the open toolchain targets best (§5.6) use **4-input LUTs**, not 6.

### 5.3 The routing fabric — and why it dominates

Logic elements sit in a grid; between them is a **programmable interconnect**: wire segments
of various lengths, and **switch boxes** of SRAM-controlled pass transistors that connect
segments.

**This is the single most under-taught fact about FPGAs: routing dominates both area and
delay.** Commonly cited figures put interconnect at the substantial majority of an FPGA's die
area — most of the chip is wires and the switches that configure them, not logic. And a
signal's delay is mostly the time spent traversing those switches, not computing in LUTs.
Each programmable switch is a transistor with resistance and capacitance; a long route
crosses many.

Consequences that shape everything else:

- **Placement determines timing.** Two LUTs placed adjacently might be 0.3 ns apart; placed
  across the die, 5 ns. Same logic, 15× the delay. This is why place-and-route takes so long
  and why its stochastic nature (§4.4) shows up in your timing report.
- **Congestion is a real failure mode.** A design that fits in logic can fail to route because
  too many signals need to cross one region. The tool reports a routing failure, not a
  capacity failure, and the fix is architectural, not incremental.
- **Locality is a design virtue.** Keeping related logic in one module with narrow interfaces
  helps the placer keep it physically together. Wide buses crossing the whole design are
  expensive in a way that has no software analogue.
- **An FPGA is ~10–20× slower and much larger than an ASIC of the same logic** (§6.3), and
  routing is the main reason.

### 5.4 Memory: block RAM vs. distributed RAM

**Block RAM (BRAM)** — dedicated hard SRAM blocks in columns across the die. On Xilinx
7-series, 36 Kb blocks, usable as one 36 Kb or two independent 18 Kb blocks, with
configurable aspect ratios (32K×1 through 512×72) and **true dual-port** operation: two
independent read/write ports, optionally in different clock domains — which is precisely what
makes the asynchronous FIFO of §4.5 buildable. Synchronous read (a registered output) is
mandatory, and that is the detail that most often breaks inference.

**Distributed RAM (LUTRAM)** — SLICEM LUTs used as memory (§5.2), 64 bits per LUT. Small,
fast, **asynchronous read** available, scattered anywhere in the fabric. Right for small
buffers, register files and lookup tables of a few dozen entries.

| | Block RAM | Distributed RAM |
|---|---|---|
| Size | Kilobits per block | 64 bits per LUT |
| Quantity | tens to thousands of blocks | any SLICEM |
| Read | synchronous only | sync or **async** |
| Ports | true dual-port | 1 write, 1–2 read |
| Cost | free if unused, else nothing | consumes logic LUTs |
| Use for | frame buffers, FIFOs, caches | register files, small LUTs |

**The inference trap, and the practical rule:** whether you get BRAM or LUTRAM is decided by
*how you wrote the RTL*, not by a declaration. Add an asynchronous read to something you
wanted in BRAM and it silently becomes thousands of LUTs. **Register the read address, and
check the utilisation report** (§4.3). This is the most common "why does my design not fit"
cause.

A Part 0 tie-in: the Hack RAM16K built from recursive `RAM8` ascent is *exactly* the thing
that should become one block RAM. Watching a hand-built memory hierarchy collapse into a
single hard primitive is a good, concrete lesson about what "technology mapping" means.

### 5.5 DSP slices — and why FPGAs can do signal processing and inference at all

Multipliers built from LUTs are large and slow, and multiplication is the core operation of
signal processing, so FPGAs include **hard multiply-accumulate blocks**.

The structure — a Xilinx DSP48-family slice — is a **pre-adder, a multiplier, and an
accumulator/ALU** in a pipelined chain, roughly:

```
   A ---> [ pre-adder ] ---\
   D --->                   [ MULTIPLIER ] ---> [ ALU / ACCUMULATOR ] ---> P
   B ------------------------/                      ^
   C ----------------------------------------------/
                                                  (feedback for accumulate)
```

Why this exact shape: it is a **multiply-accumulate (MAC)**, `P += A * B`, which is the inner
loop of a dot product, an FIR filter, a matrix multiply and a convolution. The pre-adder
exists because symmetric FIR filters compute `(x[n] + x[n-k]) * h`, halving the multipliers
needed. Dedicated **cascade paths** let DSP slices chain directly to their neighbours without
using general routing (§5.3), so a systolic filter or matrix-multiply array runs at full
clock rate.

**Why it makes FPGAs viable for DSP and inference:** a mid-range FPGA has hundreds to
thousands of DSP slices, all operating **in parallel every cycle**. A device with 2,000 DSPs
at 300 MHz is 600 GMAC/s of fully deterministic, low-latency arithmetic, with a custom
datapath around it and no instruction fetch. For **fixed-point and low-precision** work
especially — and modern parts add native INT8 modes with multiple INT8 MACs per slice — this
is genuinely competitive.

*(Exact DSP48E1/E2 bit widths are stated in §8 as unverified: AMD's UG479 returned HTTP 404
on two URL forms during this research.)*

### 5.6 Clocking, I/O and hard blocks

**Clock management (PLL / MMCM / DCM).** Dedicated analog blocks that take a reference clock
and produce multiple derived clocks with multiplied/divided frequency, controlled phase
shift, and jitter filtering. A design usually has one external oscillator and several internal
domains, which is one of the main reasons CDC (§4.5) is unavoidable in practice. Clocks are
distributed on **dedicated low-skew global clock networks** — a clock must *never* be routed
on general fabric, and routing a clock through a LUT (for gating) is a classic beginner error
that destroys skew guarantees. If you need a gated clock, use a clock enable on the flop
instead.

**I/O banks and standards.** Pins are grouped into banks sharing a supply voltage, and each
bank supports a range of electrical standards — LVCMOS at various voltages, LVDS and other
differential pairs, SSTL for DRAM. Each I/O includes programmable drive strength, slew rate,
termination, and often an input delay element and SerDes for source-synchronous interfaces.
**Bank voltage is a physical constraint that shapes pin assignment**: two peripherals needing
different I/O voltages cannot share a bank. This is where HDL meets a circuit board and a
constraints file, and it is where a first FPGA project usually stalls.

**Hard blocks.** Anything needed by nearly everyone and expensive in fabric is built as fixed
silicon: PCIe endpoints, multi-gigabit **transceivers** (SerDes running at 10–100+ Gb/s for
Ethernet, PCIe, custom links), Ethernet MACs, memory controllers, ADCs.

**SoC FPGAs** are the big one: **hard ARM cores on the same die as the fabric.** AMD/Xilinx
**Zynq-7000** (dual Cortex-A9) and **Zynq UltraScale+** (quad Cortex-A53 plus Cortex-R5),
Intel/Altera **Cyclone V SoC** and **Agilex**, Microchip **PolarFire SoC** (RISC-V). The
processor is a real hardened CPU running Linux, connected to the fabric by wide AXI ports.

The architectural point worth teaching: **this is the honest answer to "CPU or FPGA?" — it is
both.** Control, networking, filesystems and user interface go on the ARM; the tight,
deterministic, parallel datapath goes in the fabric; AXI moves data between them. Almost every
serious modern FPGA product is shaped this way, and it makes the CPU-vs-spatial-computing
trade concrete rather than rhetorical.

### 5.7 Vendors and toolchains

**Vendors.** **AMD (Xilinx)** — the market leader; Artix/Kintex/Virtex, Zynq SoCs, Versal
"ACAP". **Intel (Altera)** — Cyclone (low cost), Arria, Stratix, Agilex; note Altera was spun
back out as a standalone company in 2025. **Lattice** — small, low-power, cheap: iCE40,
MachXO, ECP5, CertusPro. **Microchip (Microsemi)** — PolarFire, flash-based, low power,
radiation-tolerant parts for space. **Gowin**, **Efinix**, **Cologne Chip** — smaller players,
increasingly relevant because the open toolchain supports them.

**Vendor toolchains: AMD Vivado, Intel Quartus.** Free editions cover smaller devices.
Enormous (tens of GB), slow, GUI-centric though fully scriptable in Tcl, and they are the only
route to large modern parts. They include synthesis, implementation, timing analysis, an
IP catalogue and hardware debug (ILA/SignalTap — on-chip logic analysers that capture
waveforms from a running FPGA, which is a genuinely important and under-taught tool).

**The fully open-source flow**, and it is real:

```
   SystemVerilog
        |  YOSYS                 (synthesis; yosys -p "synth_ice40 -json out.json")
        v
   JSON netlist
        |  NEXTPNR               (place & route, timing-driven)
        v
   Placed & routed design
        |  icepack / ecppack     (bitstream, from Project IceStorm / Project Trellis)
        v
   .bin  ->  iceprog / openFPGALoader  ->  the board
```

**nextpnr architecture support, verified from the project repository:**

| Status | Architecture | Bitstream project |
|---|---|---|
| **Stable** | Lattice **iCE40** | Project IceStorm |
| **Stable** | Lattice **ECP5** | Project Trellis |
| **Stable** | Lattice **Nexus** | Project Oxide |
| **Stable** | **Gowin** LittleBee / Aurora V | Project Apicula |
| **Stable** | **NanoXplore** NG-Ultra | Project Beyond |
| **Stable** | **Cologne Chip GateMate** | Project Peppercorn |
| Experimental | Intel **Cyclone V** | Mistral |
| Experimental | Lattice **MachXO2** | Project Trellis |
| Experimental | **Xilinx 7-series** | Project X-Ray |

**So: which boards does the open flow actually support?** The honest answer for a curriculum
is **iCE40 and ECP5** — those are the mature, stable, well-documented targets, and the ones
with a decade of community use behind them. Concretely:

- **iCE40** — Lattice iCEstick (~$25–30), iCEBreaker, TinyFPGA BX, Alchitry Cu, Icebreaker
  Bitsy. Small parts (a few thousand LUT4s), perfect for a first bitstream, and **the
  reference target for the entire open ecosystem**. The Part 0 CPU fits comfortably.
- **ECP5** — ULX3S, OrangeCrab, ColorLight repurposed LED-panel boards (famously cheap).
  Substantially larger (up to ~85K LUTs), enough for a RISC-V SoC running Linux.

Xilinx 7-series via Project X-Ray is **experimental** — do not build a course on it; that is
where a learner should reach for Vivado instead.

**Why the open flow matters pedagogically**, beyond ideology: it is small, fast, scriptable,
installable with `pip install yowasp-yosys yowasp-nextpnr-ice40`, and **every intermediate
stage is inspectable text or JSON.** Vivado is a black box that takes twenty minutes; Yosys
prints exactly what it inferred in two seconds (§0.4), and you can read the netlist. For
teaching *what synthesis does*, that transparency is worth more than device support.

### 5.8 High-level synthesis, honestly

**HLS** compiles C, C++ or OpenCL into RTL. Vitis HLS (AMD), Intel HLS, and the open-source
**Bambu** and **XLS**. You annotate loops and arrays with pragmas (`#pragma HLS pipeline`,
`unroll`, `array_partition`, `dataflow`) and the tool builds a datapath and a state machine.

**When it genuinely works:**

- **Regular, compute-bound, streaming kernels** with static loop bounds and predictable
  access patterns — image filters, FFTs, matrix multiply, convolution. This is HLS's home
  ground and it is genuinely productive there.
- **Design space exploration.** Change a pragma, get a different area/throughput point in
  minutes. Doing that by hand in RTL is days of work. This is arguably HLS's strongest real
  argument.
- **Porting existing C algorithms** where a validated reference implementation already exists.
- **Software engineers on a hardware team**, as an on-ramp.

**When it does not:**

- **Control-dominated logic.** Protocol engines, bus interfaces, arbiters, anything that is
  fundamentally a state machine. Writing the FSM directly is shorter, clearer and better.
- **Anything with hard timing or cycle-exact I/O requirements.** You do not control the
  schedule; the tool does.
- **When you need the last 20% of performance or area.** Hand-written RTL wins, sometimes by
  a lot.
- **Pointer-heavy, dynamically-allocated, or irregular code.** Not representable.

**The honest assessment:** HLS is a real, useful, deployed technology in a specific niche —
and it is *not* "write C, get hardware." Productive HLS requires understanding the hardware
you want and then writing C **in a style that coerces the tool into producing it**, plus
pragmas that are effectively a second language. Practitioners routinely report that they must
think in RTL and write in C, which is arguably the worst of both worlds for a beginner.

**For this curriculum: mention HLS, do not teach it.** A learner who does not yet know what
hardware their code becomes cannot use a tool whose entire difficulty is controlling what
hardware their code becomes. HLS is a thing to reach for *after* RTL fluency, not instead of
it — and saying so plainly protects the learner from a genuinely common wasted month.

### 5.9 What FPGAs are actually good at

**Genuinely good:**

- **Low-latency, deterministic I/O.** This is the strongest case and the least replaceable.
  React to an input in a *guaranteed* fixed number of nanoseconds, every time, with no OS, no
  interrupt jitter, no cache miss, no scheduler. High-frequency trading (wire-to-wire in tens
  of nanoseconds), motor control, hardware-in-the-loop test, scientific instrument triggering,
  software-defined radio. **A CPU cannot make this guarantee at any clock speed**, and that is
  an architectural fact, not a performance gap.
- **Custom datapaths and bit-level work.** Arbitrary precision (a 7-bit multiplier costs 7
  bits of hardware), bit permutations, CRCs, ciphers, Reed–Solomon, compression. Operations
  that take a CPU many instructions can be one cycle of wires. Bit-twiddling is where FPGAs
  humiliate CPUs.
- **Massive fine-grained parallelism with irregular structure**, where GPU SIMD lanes would
  diverge and stall.
- **Prototyping and emulation.** Verifying an ASIC before tapeout; FPGA emulation farms are
  standard practice and a major commercial market.
- **Interface bridging and glue.** Talking to an odd sensor, a legacy bus, or many parallel
  low-speed links at once.
- **Long product lifetimes and low volume**, where ASIC NRE (§6.2) cannot be amortised, and
  **field upgradability** of the hardware itself.

**Where a CPU wins:** anything irregular, branchy, or pointer-chasing; anything needing a
large memory footprint or an OS; anything where development time dominates. A CPU is a few
dollars, has enormous memory bandwidth to DRAM, and is programmed in a day.

**Where a GPU wins:** dense regular floating-point throughput. A GPU has vastly higher
FLOP/s, far more memory bandwidth (HBM), a mature software stack, and is programmed in CUDA
in an afternoon. For training, and for large-batch inference, it is not close.

**FPGAs for deep learning inference — the honest answer.** The pitch is real: custom
precision (INT8, INT4, binary), no instruction overhead, dataflow architectures that keep
weights on-chip, and genuinely excellent **latency at batch size 1**. Microsoft's Project
Brainwave deployed FPGAs for exactly this at scale.

But:

1. **GPUs adopted low precision.** Tensor cores do INT8/FP8/FP4 natively at throughput an
   FPGA cannot match. The precision advantage that motivated FPGA inference has largely
   evaporated.
2. **Memory bandwidth.** Most FPGAs have DDR4 where a datacentre GPU has HBM — an order of
   magnitude apart. Modern inference is memory-bound, so this is often decisive.
3. **The toolchain gap is brutal.** PyTorch to GPU is one line. PyTorch to FPGA is a
   research project, and any model change may mean re-synthesising for hours.
4. **Dedicated ASICs took the high end.** Where volume justifies it, TPUs and NPUs beat FPGAs
   on every axis, because they are what an FPGA is emulating.

**Conclusion: FPGAs are not competitive for mainstream deep learning inference, and the
"FPGAs will beat GPUs at AI" thesis of the late 2010s did not pan out.** They remain genuinely
good where **latency at batch 1 is the hard requirement** and throughput is not — real-time
control loops, in-line network packet inference, low-power edge devices with a fixed model, or
custom operators no GPU implements. It is a real but narrow niche. Say this plainly; the
field's marketing does not, and a learner deserves the honest version.

## 6. The bridge to ASIC

### 6.1 What changes

The RTL barely changes. **Everything below it changes completely.**

On an FPGA you configure a pre-manufactured device: the LUTs, flops, BRAMs and routing
already exist in silicon, and the bitstream tells them what to be. On an ASIC **you are
manufacturing the transistors**, which means you now own every physical question the FPGA
vendor had already answered for you.

**Standard cell libraries.** Instead of LUTs, the synthesiser maps to a **library of
pre-designed, pre-characterised logic cells** — INV, NAND2, NOR3, AOI21, DFF, DFF with
scan, and so on, typically several hundred cells, each in multiple **drive strengths** (a
NAND2_X1 through NAND2_X8, physically larger, faster into heavy loads, more power). All cells
share a fixed height so they abut in rows. The library ships as **Liberty (`.lib`)** timing
and power models, **LEF** abstract physical views, and **GDSII** full layout.

**This is where "gate count" becomes real again**, and it is a nice reversal for the learner:
on an FPGA, XOR and AND cost the same (§5.1); on an ASIC, XOR really is more transistors than
NAND, exactly as Part 0's gate-counting implied. The Part 0 intuition was not wrong, it was
just aimed at the wrong target.

**The flow:**

```
   RTL
    |  SYNTHESIS -> standard cell netlist, timing-driven, against .lib models
    v
   Gate-level netlist
    |  FLOORPLAN     -- die size, macro placement (RAMs, PLLs), power grid, I/O ring
    v
    |  PLACEMENT     -- every standard cell gets a legal row position
    v
    |  CTS (Clock Tree Synthesis)  -- build a balanced buffer tree to every flop
    v
    |  ROUTING       -- detailed metal on 5-15+ layers
    v
    |  SIGN-OFF      -- STA at all PVT corners, DRC, LVS, antenna, IR drop, EM
    v
   GDSII  ->  mask making  ->  fab  ->  wafer  ->  test  ->  package
```

Steps with no FPGA equivalent, and they are the ones that surprise people:

- **Floorplanning.** You decide the die's shape, where the hard macros sit, how power is
  distributed, and where the pads go. Get it wrong and nothing routes.
- **Clock tree synthesis.** The FPGA *gave* you a global clock network with guaranteed low
  skew (§5.6). On an ASIC **you build it**, inserting hundreds or thousands of buffers to
  deliver the clock to every flop with balanced delay. Clock skew is now a design output, and
  it feeds straight back into the setup and hold equations of §4.4. CTS also consumes a
  significant share of total chip power.
- **DRC (Design Rule Check).** Does the layout obey the foundry's geometric rules — minimum
  widths, spacings, density, antenna ratios? Thousands of rules; violations are not
  manufacturable.
- **LVS (Layout Versus Schematic).** Does the physical layout actually implement the netlist?
  This catches the catastrophic class of bug where place-and-route quietly did something
  wrong.
- **Sign-off timing across PVT corners.** Slow/typical/fast process × voltage range ×
  temperature range, plus on-chip variation. Dozens of corners, all of which must pass.
- **DFT (Design For Test).** Scan chains stitched through every flop so the fabricated chip
  can be tested, plus BIST for memories. Perhaps 5–10% area overhead, and non-optional —
  an untestable chip is an unsellable chip.
- **Tapeout.** Send GDSII to the foundry. **It is final.** There is no patch, no hotfix, no
  redeploy. This is the most alien fact in the entire subject for a software learner and it
  deserves to be stated bluntly: **a bug found after tapeout costs millions of dollars and
  months.** That single asymmetry explains why verification is half the project (§3) and why
  the industry's culture is what it is.

### 6.2 NRE and mask costs — why this is not a weekend project

**NRE (Non-Recurring Engineering)** is everything you pay before the first working chip:
tools, IP licences, engineering time, and **masks**.

A mask set is a collection of precision photolithographic plates, one or more per layer, 40+
layers on a modern process. Cost scales sharply with node — a mature node like 130 nm or
180 nm might be low hundreds of thousands of dollars for a mask set; a leading-edge node runs
into many millions, and total NRE for a leading-edge SoC (masks plus EDA licences plus IP
plus a large team) is routinely quoted in the tens to hundreds of millions.

Consequences that follow directly:

- **Volume is everything.** NRE amortises across units. At a million units a $2M NRE is $2 a
  chip; at a thousand units it is $2,000 a chip. **This is the whole economic case for
  FPGAs**, and it is a cleaner explanation than any technical argument.
- **Respins are catastrophic.** A functional bug requiring new masks costs the mask set again
  plus months of schedule. Hence verification (§3), hence formal (§3.9), hence why "we think
  it works" is not an acceptable answer.
- **Older nodes stay alive.** 180 nm, 130 nm and 65 nm remain in volume production because
  for most chips they are cheap, adequate and low-risk. Leading edge is for products where
  performance per watt justifies the cost.
- **MPW (Multi-Project Wafer) shuttles** exist precisely to break this wall: many designs
  share one mask set and one wafer run, splitting the NRE. This is the mechanism that makes
  §6.4 possible at all.

### 6.3 Why an FPGA costs an order of magnitude

The standard, widely-cited comparison — originating in Kuon & Rose's measurement study
(*"Measuring the Gap Between FPGAs and ASICs"*, FPGA 2006) and still the reference figure —
is that for logic-only designs an FPGA costs roughly:

- **~35× the area**
- **~3–4× the critical-path delay**
- **~10–14× the dynamic power**

versus a standard-cell ASIC in the same process. (Designs that make heavy use of hard blocks
— BRAM, DSP — close the gap considerably, since those *are* hardened; the ~35× is the
worst case for pure random logic.)

**Where the cost goes**, and this is the satisfying part because it all follows from §5:

- **Routing.** Most of the die is programmable interconnect and configuration SRAM (§5.3).
  An ASIC's wires are just wires.
- **Configuration memory.** Every LUT bit, every routing switch, needs an SRAM cell holding
  it — memory that does no computation and burns static power.
- **Programmable switches.** Every connection passes through pass transistors with resistance
  and capacitance, instead of a direct metal wire.
- **Granularity.** A LUT implementing a 2-input AND wastes most of its 64 SRAM bits. An ASIC
  instantiates a 2-input AND cell.

**And what you buy for it:** no NRE, no masks, no tapeout risk, a design cycle measured in
minutes instead of months, field-upgradable hardware, and the ability to fix a bug by
reflashing. **Configurability is the product, and an order of magnitude in area, power and
speed is its price.** That framing — you are paying ~35× area for the right to change your
mind — is the cleanest way to state the trade.

### 6.4 Open-source silicon — and the genuinely remarkable capstone

Until recently, tapeout was categorically out of reach for an individual: proprietary PDKs
under NDA, six-figure EDA licences, six-figure mask costs. **That changed, and the change is
worth calling out as one of the more remarkable developments in the field.**

**Open PDKs.** In 2020 Google and SkyWater released **SKY130**, a 130 nm process design kit,
**fully open source** — the first time the physical design rules, device models and standard
cell libraries for a real, manufacturable process were public. GlobalFoundries followed with
**GF180MCU** (180 nm). **IHP** released the **IHP Open PDK** for **SG13G2**, verified from its
repository as "a high performance BiCMOS technology with a 0.13 μm CMOS process" including
**SiGe:C npn-HBT bipolar devices reaching up to 350 GHz transition frequency**, dual gate
oxides (1.2 V and 3.3 V), five thin and two thick metal layers with MIM capacitors, released
under **Apache 2.0**. IHP is notable for being open **and** RF-capable — SKY130 has no
BiCMOS/HBT — and for being backed by a real foundry with a production history. Supported by
ngspice, Xyce, xschem, KLayout, Magic, OpenROAD and LibreLane.

**Open EDA: OpenLane / LibreLane.** OpenLane wraps **Yosys** (synthesis), **OpenROAD**
(floorplan, placement, CTS, routing, STA), **Magic** and **KLayout** (DRC, GDS), and
**Netgen** (LVS) into a push-button RTL-to-GDSII flow.

**An important status correction:** the brief refers to OpenLane and Efabless, and both have
changed.

- **Efabless has ceased operations.** `efabless.com` now returns **HTTP 301 redirecting to
  `chipfoundry.io/efabless`**, which states that "**Umbralogic Technologies LLC, doing
  business as ChipFoundry, has acquired the assets of Efabless Corporation.**" ChipFoundry
  continues the **chipIgnite** shuttle programme. Efabless' open MPW programme, which
  originally made this accessible, is gone in its original form.
- **OpenLane 2 has been forked into LibreLane**, maintained by the **FOSSi Foundation** and
  described in its repository as "ASIC implementation flow infrastructure, successor to
  OpenLane." UmbraLogic "has agreed to relicense all OpenLane 2 Nix code as MIT", enabling
  the fork. **For a 2026 curriculum, point at LibreLane and the FOSSi Foundation, not
  Efabless.**

**TinyTapeout — the actual capstone, and it is real.** TinyTapeout aggregates many tiny
designs onto one shared shuttle, splitting the mask cost hundreds of ways. Verified from the
project site:

- **Processes: SKY (SkyWater 130 nm), IHP, and GF (GlobalFoundries 180 nm).** Shuttles run on
  a rolling schedule; at the time of checking, **SKY26c** and **IHP26b** were both open with
  44 days remaining.
- **A tile is approximately 160 × 100 µm and holds about 1000 digital logic gates.** Designs
  can be 1×1, 1×2, 2×2 or larger.
- The flow is **Verilog → OpenLane → GDS**, with Wokwi available for visual entry and Magic
  for custom layout.
- Participants receive a **devkit**: a demo board plus a breakout board carrying the
  fabricated ASIC, with microcontroller firmware ("Tiny Tapeout Commander") to drive it.

**Roughly a thousand logic gates is small — and it is enough.** A learner who built the Part 0
CPU can fit a meaningfully-sized piece of it, and the point is not the design's size. **The
point is that an individual can now send a design to a real foundry for a few hundred dollars
and receive, in the post, a physical chip containing logic they wrote.** That is a genuinely
new state of affairs — it was impossible at any price for an individual fifteen years ago —
and it is an extraordinarily strong ending for a course that began at NAND gates. **It should
be called out explicitly as the capstone opportunity it is.**

*(Exact current pricing was not verifiable: TinyTapeout's calculator at
`app.tinytapeout.com/calculator` is a client-side application and returned no content to a
plain fetch. The site directs users there for live prices and mentions limited early-bird
discounts for individuals. See §8.)*

## 7. Curriculum

Four units, in dependency order, positioned **immediately after the Part 0 NAND-to-CPU
material as its continuation into real hardware**, plus an optional capstone. Each has ONE
idea. Every exercise names its checking mechanism, per §0.

**A note on sequencing.** The natural instinct is to open with Verilog syntax. Do not. Unit 1
spends its entire length on the structure-vs-sequence inversion (§1), because a learner who
does not internalise it writes syntactically valid Verilog that is conceptually software, and
every later unit compounds the error.

---

### Unit 1 — Structure, Not Sequence

> **THE ONE IDEA: Your code is not executed. It is *built*. Everything exists at once,
> forever, and settles.**

**Prerequisites:** Part 0 complete (NAND → gates → ALU → CPU in the teaching HDL).

**Positioning.** Open by validating what they already have: nand2tetris' HDL is purely
structural and their instinct is *correct*. Then warn them Verilog's C-like syntax will
attack that instinct, and that the job of this unit is to defend it (§1.7).

**Content:** `assign` as a permanent wire, not an event (§1.2); concurrency and continuity
(§1.3); the `for` loop unrolling into space and the inverted cost model (§1.4); `reg` does not
mean register (§1.5, §2.2); modules, ports, named connection (§2.1); `logic` as the default
type; parameters and `generate` (§2.7); the synthesisable subset and why `initial` is a lie
(§2.8). The four diagnostic questions (§1.6).

**Exercises:**

1. **Translate Part 0's gates.** `Not`, `And`, `Or`, `Xor`, `Mux16`, `DMux8Way` from
   nand2tetris HDL into SystemVerilog. *Check: HDLBits has direct equivalents in Getting
   Started / Verilog Language / Combinational Logic, auto-graded in the browser.*
2. **`Add16` two ways.** Write it once as sixteen hand-instantiated full adders (as in Part
   0), then again as a `generate` loop. *Check: `yosys -p "read_verilog X.v; synth; stat"` on
   both — **assert identical cell counts**. This is the "the loop is in the compiler, not the
   chip" lesson made numeric.*
3. **The cost of a loop.** Write an 8-bit, then 16-, then 32-bit parity tree. Plot LUT count
   vs. width. *Check: Yosys `stat`. The learner discovers area scales with the loop bound —
   §1.4's table, measured.*
4. **Reimplement the Part 0 ALU** in SystemVerilog: the six control bits `zx nx zy ny f no`,
   outputs `out`, `zr`, `ng`. *Check: self-checking testbench in Icarus exhaustively covering
   all 64 control encodings × a vector set, printing PASS/FAIL (§3.2). **Plus** the Yosys SAT
   equivalence proof of §0.4(c) against a behavioural golden model — proving it for all
   inputs, not sampling.*

**Tooling:** HDLBits (browser, zero install) for the drills; `pip install yowasp-yosys` for
everything structural; Icarus locally for the testbench. Optionally, the SystemC example on
Compiler Explorer (§0.3) as a shareable in-browser demonstration of concurrency.

---

### Unit 2 — The Clock Edge

> **THE ONE IDEA: There are exactly two kinds of logic — combinational, which settles, and
> sequential, which samples on an edge. Almost every bug in this language is a confusion
> between the two.**

**Prerequisites:** Unit 1.

**Positioning.** Part 0 handed the learner a DFF as an axiom and never explained the clock as
anything but a time unit. This unit makes the edge the central object.

**Content:** flip-flops and `always_ff` (§2.4); **blocking vs non-blocking, with the event
queue** (§2.3) — the centrepiece of the unit; `always_comb`, `always_ff`, `always_latch` and
why the split exists; **inferred latches** (§2.5); sensitivity lists and the classic bug
(§2.6); FSM coding style; resets, sync vs async, assert-async/deassert-sync (§4.6).

**Exercises:**

1. **The one-character exercise.** Given a two-flop module, write it with `<=`, synthesise,
   record the cell count. Change both to `=`, synthesise again. **Predict the result before
   running it.** *Check (verified, §0.4(b)): `yosys -p "read_verilog X.v; synth -top shifter;
   stat"` reports **`2 $_DFF_P_`** for `<=` and **`1 $_DFF_P_`** for `=`. A grader greps the
   DFF count. Follow up by simulating both in Icarus and reading the waveform to see the
   missing cycle.* This is the highest-value exercise in the unit and possibly the course.
2. **Find the latch.** Hand the learner a plausible-looking ~40-line control decoder for the
   Part 0 CPU containing **one** `case` with a missing branch. Do not tell them where. Task:
   run synthesis, find the latch **from the warning alone**, explain why it happened, fix it
   three different ways (default assignment, complete the `case`, `always_comb`). *Check
   (verified, §0.4(a)): success is `yosys ... stat` reporting **zero `$dlatch` cells** and no
   `Latch inferred for signal` warning. Also point them at HDLBits' "If statement latches" and
   "Avoiding latches" for extra drilling.*
3. **The sensitivity-list mismatch.** Give them `always @(a or b) y = a & b & c;`. Simulate in
   Icarus (wrong), synthesise in Yosys and inspect the netlist (right). *Check: the learner
   must explain the discrepancy. This is the simulation/synthesis mismatch made concrete
   rather than described.*
4. **Rebuild the Part 0 CPU** — `CPU.hdl` in real SystemVerilog: A and D registers, PC with
   reset/load/inc priority, instruction decode, ALU wiring. *Check: a self-checking testbench
   that runs a known Hack program and compares the architectural state against the
   nand2tetris CPU emulator's trace, cycle by cycle — a golden-model comparison (§3.2, level
   3).*

### Unit 3 — Proving It Works

> **THE ONE IDEA: Verification is the job. A design is a claim, and you have to prove it —
> and for hardware, unlike software, you sometimes actually can.**

**Prerequisites:** Unit 2 (you need something worth verifying).

**Positioning.** State the ratio up front (§3.10). The learner has just built a CPU and feels
finished; the unit's opening move is to show them they are about halfway.

**Content:** event-driven simulation and the delta cycle (§3.1) — this retroactively explains
Unit 2's `<=` rule, which is why it lands better here than earlier; testbench maturity levels
(§3.2) and the `!==` trap; Verilator, what it is, why it is fast, and its 2-state limitation
(§3.3); Icarus and the open flow (§3.4); **waveform reading as a taught skill** (§3.5);
assertions and SVA (§3.6); constrained-random and coverage in concept (§3.7, §3.8); UVM
described honestly and not taught; **formal property verification and equivalence checking**
(§3.9).

**Exercises:**

1. **Waveform archaeology.** Provide a VCD of the Unit 2 CPU running a program, with a bug
   injected. The learner finds the first divergent cycle and identifies the faulty signal.
   *Check: they name the signal and cycle. Teaches bisection-in-time (§3.5).*
2. **Annotate the fetch–execute cycle from a waveform.** Mark where each phase begins and
   ends. *Directly repairs the Part 0 gap: the Hack CPU is single-cycle, so the learner has
   never seen an instruction take time (§1.7).*
3. **Verilator + C++ golden model.** Wrap the CPU in a C++ testbench, with a simple
   instruction-set simulator as the reference, comparing all architectural state every cycle.
   *Check: the harness prints PASS/FAIL and the first mismatching cycle. Also: run it with
   `--x-assign unique` under several seeds and discuss why 2-state simulation might hide a
   reset bug (§3.3).*
4. **Assertions on the CPU.** Write SVA for: the PC never takes an `x`; a jump is taken only
   when the condition bits agree; the state encoding stays one-hot. *Check: assertions fire in
   simulation on deliberately broken variants.*
5. **Prove the ALU.** Yosys SAT miter against a behavioural golden model. Then break it (drop
   the carry-in) and read the counterexample. *Check (verified, §0.4(c)): `SAT proof finished
   - no model found: SUCCESS!` for the correct version; a concrete counterexample for the
   broken one. **The learner should be asked to reflect on the difference between this and
   Part 0's test vectors** — sampling versus proof.*

---

### Unit 4 — Timing, and the Chip It Runs On

> **THE ONE IDEA: The longest combinational path between two registers sets your clock speed
> — and a circuit that is too slow is not slow, it is *wrong*.**

**Prerequisites:** Unit 3.

**Positioning.** This is where "hardware" becomes physical. It is also where the course
connects hardest to the architecture units, and that connection should be foregrounded rather
than left implicit.

**Content:** the synthesis flow end to end (§4.1); inference and the utilisation report
(§4.2, §4.3); **static timing analysis** — setup, hold, clock-to-Q, critical path, slack,
Fmax (§4.4), including why hold violations cannot be fixed by slowing the clock; **CDC,
metastability, MTBF, synchronisers, async FIFO with Gray pointers** (§4.5); resets (§4.6);
**pipelining and retiming, connected explicitly to CPU pipelining** (§4.7); FPGA architecture
— LUTs, slices, routing dominance, BRAM vs LUTRAM, DSP slices, clocking, I/O, SoC FPGAs
(§5.1–5.6); vendors and the open toolchain (§5.7); HLS briefly and honestly (§5.8); what
FPGAs are and are not good for, including the honest DL-inference answer (§5.9).

**Exercises:**

1. **Compute Fmax by hand.** Given: `t_cq = 0.4 ns`, a combinational path of a 16-bit ripple
   carry adder at `0.25 ns` per stage, a 4:1 mux at `0.3 ns`, `t_setup = 0.2 ns`, clock skew
   `0.1 ns`. Compute the critical path, `T_clk`, and `Fmax`. Then: the target is 200 MHz —
   what is the slack, and how many pipeline stages are needed to close it?
   *Worked answer: `t_comb = 16 × 0.25 + 0.3 = 4.3 ns`; `T_clk ≥ 0.4 + 4.3 + 0.2 + 0.1 =
   5.0 ns`; `Fmax = 200 MHz` exactly, slack = 0. Then ask what happens at 250 MHz (slack
   = −1.0 ns, fails) and have them pipeline the adder into two 8-bit halves.
   Check: arithmetic, plus a written justification.*
2. **Find and fix a critical path for real.** Synthesise the Unit 2 CPU for an iCE40, read the
   timing report, identify the critical path, pipeline it, and re-measure. *Check:
   `nextpnr-ice40` reports an estimated Fmax before and after — a real number that must
   improve. Available via `pip install yowasp-nextpnr-ice40`, no vendor tools.*
3. **The pipelining bridge.** Having pipelined the datapath, ask: what breaks? Answer:
   instructions now overlap and a result may not be written back before the next instruction
   needs it. **Have them discover data hazards from a timing fix, then read the architecture
   unit's forwarding material.** *This is the §4.7 connection, made by discovery rather than
   assertion, and it is the strongest single link between this part and the rest of the
   course.*
4. **Async FIFO with Gray-coded pointers.** Build it: dual-port memory, binary counters, Gray
   conversion, two-flop synchronisers each way, full/empty from the extra-MSB trick. *Check:
   a testbench with two deliberately incommensurate clock frequencies (e.g. 100 MHz and
   37 MHz), random write and read pressure, asserting no overflow, no underflow, and data
   integrity in order. Then the instructive part: **replace the Gray counter with a plain
   binary one and demonstrate the corruption.** Also add SVA `assert property (!(full &&
   push))`.*
5. **Blink an LED on real hardware.** Bitstream via `yosys → nextpnr-ice40 → icepack →
   iceprog` onto an iCEstick or iCEBreaker (~$25–30, §5.7). *Check: the LED blinks. Not
   machine-checkable and that is entirely the point — it is the moment the course's title
   becomes true.*
6. **Read the utilisation report.** Write a small memory two ways — registered read address vs
   asynchronous read — and compare BRAM vs LUT usage. *Check: Yosys `stat`. The learner sees
   an inference failure cost thousands of LUTs (§5.4).*

### Capstone (optional) — Tapeout

> **THE ONE IDEA: You can send this to a foundry and get a physical chip back.**

Not a unit so much as an invitation, and it should be offered explicitly because most learners
do not know it is possible.

**Content:** what changes for ASIC — standard cells, the flow, CTS, DRC/LVS, sign-off (§6.1);
NRE and mask economics, and why FPGAs exist (§6.2); the ~35× area / ~3–4× delay / ~10× power
cost of configurability (§6.3); open PDKs (SKY130, GF180MCU, IHP SG13G2), **LibreLane** under
the FOSSi Foundation, and the Efabless → ChipFoundry status change (§6.4).

**Exercise:** take the Unit 2 ALU (or a trimmed CPU) through **LibreLane** to GDSII against
SKY130, inspect the layout in KLayout, and — for anyone who wants to — submit to a
**TinyTapeout** shuttle: ~1000 gates per 160 × 100 µm tile, a few hundred dollars, and a
physical chip in the post. *Check: a clean GDS with DRC and LVS passing.*

Even for learners who do not submit, running the flow and looking at the polygons closes the
loop that Part 0 opened at NAND. It is worth doing for that alone.

## 9. Addendum — additional tooling checks (independent re-verification, 2026-09-01)

The §0 findings were independently re-run against the live Compiler Explorer API. **All of
§0's conclusions reproduced.** The following are additional data points not recorded above.

**9.1 The compiler-list sweep, quantified.** `GET /api/compilers?fields=id,name,lang`
returns **6,271 compilers**. Filtering the id, name *and* lang of every one for
`veril|yosys|vhdl|chisel|firrtl|circt|iverilog|amaranth|spinal|hdl` yields **exactly one
match**: `circtopt-trunk`. This confirms §0.1 by exhaustive sweep rather than by language
list alone. Its metadata: `compilerType: mlir`, `supportsExecute: false`,
`supportsBinary: false` — so CIRCT cannot simulate anything even in principle.

**9.2 A name collision worth flagging explicitly.** Compiler Explorer lists a language
`slang` (compilers `slangc_2024_14_6` … `slangc_2026_14_1`, `shaderexplorer_slang012`).
There is a well-known open-source **SystemVerilog** frontend also called **slang**
(sv-lang.com), now used inside CIRCT's `circt-verilog`. **Compiler Explorer's `slang` is not
that project** — it is the Khronos/NVIDIA *shading* language (`compilerType: slang` /
`shader-explorer`). Anyone re-checking "is there an SV frontend on godbolt?" will hit this
and can easily conclude wrongly. There is no SystemVerilog frontend.

**9.3 SystemC 3.0.2 is now available and works.** §0.3 records versions 3.0.0 and 3.0.1.
The library list now also offers **3.0.2 (id `302`)**, and it executes: verified with
compiler `g152` (GCC 15.2) and `-std=c++17`, giving `code: 0`, `didExecute: true`, banner
`SystemC 3.0.2-Accellera`. The §0.3 ABI caveat still applies — the C++ standard is baked
into a symbol name, so **the standard flag must match the prebuilt library**; `g152` +
`-std=c++17` + `systemc/302` is a working combination alongside §0.3's pinned
`g142`/`c++17`/`301`.

**9.4 A self-checking SystemC testbench returns a usable verdict.** This is the property
that matters for auto-graded exercises and it was verified end to end. A deliberately broken
ALU (SUB implemented as ADD) driven by a 50-vector self-checking loop returned:

```
EXIT CODE: 1    didExecute: true
STDOUT: FAIL i=1 got 10 exp 4
        FAIL i=2 got 20 exp 8
        errors=49
```

Non-zero exit on failure, zero on success, diagnostics on stdout. **The in-browser SystemC
route is therefore genuinely machine-checkable**, not merely runnable.

**9.5 CIRCT lowers sequential logic, not just combinational.** §0.1 demonstrates
`--export-verilog` on the `hw`/`comb` dialects. The `seq` dialect works too: `seq.compreg`
with `--lower-seq-to-sv --export-verilog` emitted correct SystemVerilog with `always_ff`
blocks, **non-blocking assignments** and reset:

```verilog
  reg [7:0] q1;
  always_ff @(posedge clk) begin
    if (rst) q1 <= 8'h0;
    else     q1 <= d;
  end
```

This makes CIRCT a slightly better *demonstration* than §0.1 allows — it is a zero-install,
shareable illustration of a hardware compiler backend emitting exactly the `always_ff`/`<=`
idiom taught in §2.3, and it is literally the last stage of the Chisel pipeline (§2.10). It
remains useless as an exercise checker, so §0.1's verdict ("a curiosity, not a teaching
tool") stands for *authoring*, with this one narrow exception for *illustration*.

**9.6 Two further negative results.** `GET /api/libraries/python` returns an **empty list** —
so **cocotb, Amaranth, PyVerilog and MyHDL are all unavailable** on Compiler Explorer, closing
the Python routes into HDL there as well. And although `cmake` and `makefile` appear as
language ids, **no compilers are registered under either**, so there is no multi-file build
exposed through the compile API — an independent reason (beyond §0.2's missing
`libverilated.a`) that a Verilator output tree could never be assembled there.

**9.7 Net effect on §0.6's verdict: unchanged.** Compiler Explorer cannot check Verilog. The
recommended stack remains §0.4's `yowasp-yosys` and a local OSS CAD Suite, with §0.5's
HDLBits for auto-graded browser drills, and SystemC on Compiler Explorer as a zero-install
option for the one exercise where it genuinely fits — the blocking-versus-non-blocking
contrast, since **`sc_signal`'s deferred write versus a plain C++ variable's immediate write
is exactly the `<=` versus `=` distinction** of §2.3.
